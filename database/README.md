# Ename Registry — Database

Database tooling for the [Ename](https://ename.ngo) registry: schema, migrations, local development PostgreSQL cluster, and the migration runner.

This package is intentionally separated from `backend/` so the same migration corpus, schema dump, and seed data feed every consumer of the registry's PostgreSQL — the current Node phase, the upcoming Rust phase (axum + sqlx), and any future operational tooling. See [`../docs/ename-internals.md`](../docs/ename-internals.md) for the long-term architecture invariants.

## Requirements

- **Node.js ≥ 26**: relies on native TypeScript execution (no build step).
- **npm ≥ 12**: configured via `.npmrc` for supply-chain hardening (3-day release cooldown, dependency install scripts blocked unless allowlisted in `package.json`).
- **Docker** (Desktop, OrbStack, or compatible): runs the local PostgreSQL via this package's [`compose.yml`](./compose.yml).

Both versions are pinned in `mise.toml` for [mise](https://mise.jdx.dev) users.

## Setup

```bash
# Install dependencies. A dependency whose install scripts are not yet covered
# by "allowScripts" in package.json fails the install: review it, then run
# `npm install-scripts approve <pkg>` or `npm install-scripts deny <pkg>`.
npm install

# Copy the local environment file and adjust if needed.
cp .env.example .env

# Start PostgreSQL (Docker), wait for the healthcheck, then apply all migrations
# to both ename_dev and ename_test. Idempotent — safe to run on every clone.
npm run db:up
```

The local database is a single PostgreSQL 18 cluster (matching Scaleway Serverless SQL) hosting two logical databases: `ename_dev` (used by the app) and `ename_test` (used by the test runner). The cluster is defined in this package's [`compose.yml`](./compose.yml) and pulled into the repo-root [`compose.yml`](../compose.yml) via `include:`, so it can be brought up standalone from here (`npm run db:up`) or as part of the whole stack from the repo root (`docker compose up`). Both launch sites share the same project name (`ename`) and therefore the same data volume.

## Common commands

| Command                    | What it does                                                                       |
| -------------------------- | ---------------------------------------------------------------------------------- |
| `npm run db:up`            | Start PostgreSQL (Docker), wait for healthcheck, run migrations on both databases. |
| `npm run db:down`          | Stop the PostgreSQL container (data preserved in the named volume).                |
| `npm run db:nuke`          | Stop the container **and delete the data volume**. Destructive.                    |
| `npm run db:migrate`       | Apply pending migrations to `ename_dev`.                                           |
| `npm run db:migrate:test`  | Apply pending migrations to `ename_test`.                                          |
| `npm run db:new -- <name>` | Create a new empty `<unix_ts>_<name>.sql` in `migrations/`.                        |
| `npm run db:reset`         | Drop and recreate `ename_dev`, then re-run migrations. Fast reset without nuking.  |
| `npm run db:reset:test`    | Same for `ename_test`.                                                             |
| `npm run db:dump`          | Dump `ename_dev`'s schema to `schema.sql` (versioned).                             |
| `npm run db:status`        | List migrations applied to `ename_dev`.                                            |
| `npm run typecheck`        | Type-check the migration scripts (`tsc --noEmit`).                                 |
| `npm run lint`             | Lint the codebase via ESLint.                                                      |
| `npm run lint:fix`         | Lint and auto-fix where possible.                                                  |
| `npm run format`           | Check formatting via Prettier.                                                     |
| `npm run format:fix`       | Reformat the codebase via Prettier.                                                |
| `npm run check`            | Run typecheck + lint + format in sequence.                                         |

## Project structure

```
database/
├── init/
│   └── 01-create-databases.sql    # Runs once at first container boot — creates ename_test
├── migrations/                    # <unix_ts>_<name>.sql, forward-only (no down files)
├── scripts/
│   ├── migrate.ts                 # Custom migration runner (content hash + per-migration transaction lock)
│   └── new-migration.ts           # Scaffolds a new up/down migration pair
├── schema.sql                     # Canonical schema dump, regenerated by `npm run db:dump`
├── compose.yml                    # Local PostgreSQL service (included from the root compose.yml)
├── eslint.config.js
├── tsconfig.json
├── package.json
└── README.md
```

Migrations are forward-only and have no down files: a local rollback is `npm run db:reset`. The runner invariants (SHA-256 of each file's raw bytes, per-migration transaction holding a transaction-level advisory lock, lexicographic ordering, single connection) are documented inline at the top of [`scripts/migrate.ts`](./scripts/migrate.ts) and in [`../docs/ename-internals.md`](../docs/ename-internals.md); the `schema_migrations` table and the hash are the contract the Rust phase reimplements.

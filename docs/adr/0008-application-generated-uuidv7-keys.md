# Application-generated UUIDv7 primary keys, BIGINT identity for the log

Recorded retroactively; the decision dates from the initial schema (commit `7a57873`) and the events table (commit `8a7f915`).

## Context

A subject id is exposed publicly as a reference stable across platforms and renames, for centuries. A rebuild from the log must reproduce every entity row exactly (ADR-0003), so the id must be known before the INSERT. Log entries are a different thing: a position in a total order.

## Decision

Every entity table uses UUIDv7 (RFC 9562), generated by the application, stored in the native 16-byte `uuid` type, with no `DEFAULT`. Log tables use `BIGINT` IDENTITY. Ids are validated by a strict lowercase pattern at every boundary.

## Considered options

- **Serial integers for entities.** Rejected: enumerable, allocated by the database at insert time, and they leak registration counts.
- **UUIDv4.** Rejected: random insertion order defeats B-tree locality on tables that only grow.
- **ULID or another sortable id.** Rejected: not an IETF standard and no native PostgreSQL type; UUIDv7 gives the same time prefix within the ratified format.
- **Database-side generation** (`DEFAULT` with a UUID function). Rejected: a missing id would be filled silently, and a rebuild would no longer reproduce the same rows.

## Consequences

- A missing id fails loudly at INSERT.
- `subject_id` is a public, stable reference; `number_part` is a domain counter, never a key.
- A log position is serialized as a string once it may exceed 2^53.

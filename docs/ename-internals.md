# Ename registry internals

## Preamble

This document records the **internal implementation decisions** of the Ename registry — choice of stack, hosting, primary key format, API contract, etc. It is intended for the team that implements and operates the registry backend.

This document does not cover:

- the **public technical standards** that the registry publishes and that operators must implement (ename format, signature algorithms, format of inter-operator transfers, etc.) — these belong to a separate family of documents, of which `ename-format-v0.7-fr.md` is the first representative;
- the **mission, governance and institutional model** of the registry — described in `ename-synthesis.md`.

The distinction is structural: the decisions below are **unilaterally revisable** by the registry's technical team; public standards are not (mandatory prior public consultation for any structural modification, cf. `ename-synthesis.md` § Governance).

Conventions:

- **Explicit status** on decisions: `[settled]`, `[settled in principle]`, `[strong intuition]`, `[working hypothesis]`, `[open]`.
- **Stable Q-IDs** for open topics (`[Q-XXX]`), referenceable from the body. Shared with the other documents in the corpus when the question itself is shared.
- **Dense and explicit text**, as in `ename-synthesis.md`.

---

## Design posture: YAGNI on implementation, anticipation on the contract

At the **implementation** level (module breakdown, file organization, schema extraction, tooling options), the project applies YAGNI strictly: an abstraction, indirection or structure is introduced only when a concrete need appears, never in anticipation. The expected benefit must be current and identifiable, not speculative. Repeated applications in what follows:

- Flat modules at the root of each layer as long as they don't exceed half a dozen functions; switch to folder-per-use-case afterwards.
- Zod schemas inline with their consumer until reuse or loss of readability; extraction to `*/schemas/` afterwards.
- A single HTTP sub-app `api/index.ts` today; refactor into `api/v1/`, `api/v2/` the day v2 actually exists.
- `openapi.json` at the root of the backend package, not in a dedicated folder, as long as there is only one spec file.
- No Dockerfile, no CI, no deployment scaffolding until the need is concrete.

The accepted cost: at each switch (flat file → folder, inline → extracted, etc.), a small refactor is paid. Deliberate. The cost of *n* local and trivial refactors remains lower than the cost of an over-specified architecture from the start — which imposes a permanent cognitive load on reading and constrains future choices through pre-emptive structures that rarely match the actual need.

**Conversely**, on **long-lived structural commitments** — the public ename format, published cryptographic schemes, the structure of the event log, the primary key format, the choice of exposed identifiers, stabilized API contracts — the posture is the opposite: these decisions become near-irreversible once published, deserve maximum anticipation effort, and a thinking deficit costs infinitely more there than a pre-emptive indirection in code. **YAGNI applies only to what is reversible.**

## Two-phase stack strategy

The backend is implemented in two successive phases:

- **Phase 1 (~2-3 years, single operator 1Place)**: Node.js + TypeScript. Chosen for solo productivity and time-to-market during the period when 1Place is the sole operator of the registry and the API contract has no external stability commitment.
- **Phase 2 (long-term target, Rust team in place)**: Rust + axum + sqlx. Chosen for memory safety, predictable performance and the maturity of Rust on long-running network services. The port is executed by an experienced Rust team recruited for this purpose (typically 1-2 people), not by gradual migration of the Node code.

The pivot between the two phases is made viable by a structural constraint: the **canonical versioned OpenAPI spec is the language-independent contract**, of which Node and Rust are two successive implementations. All Phase Node choices are made to maximize fidelity to the target architectural model (axum/sqlx) and minimize the friction of the port.

## Registry architecture as a verifiable event log

A foundational architectural decision, prior to stack choices: the registry is implemented as an **append-only event log** whose entries are chained in a Merkle-like cryptographic structure, and which constitutes the **single source of truth** of the registry. The SQL database is only a reconstructible projection of the log, serving fast reads. The log is public and auditable by any third party — consistent with the principle of transparency and the cryptographic anchoring function of the registry (cf. `ename-synthesis.md` § Cryptographic anchoring and § Founding principles).

This model addresses the multi-century durability requirement of a commons: it makes any retroactive rewriting of history detectable, without depending solely on institutional trust in the registry operator.

Decisions:

- **Event sourcing — the log is the source of truth, the SQL database is a projection**. Every mutation of the registry (ename creation, key rotation, revocation, recovery, deactivation, operations on the log mechanics themselves) is recorded as an immutable event in the log. No retroactive modification or deletion. The SQL database is fully reconstructible by replaying the log. This choice structures the schema, the write model, the backup strategy and the registry's stance toward erasure requests (cf. [Q-LEGAL-DEMANDS]). `[settled]`
- **Public cryptographic verifiability of the log**. Events are chained in a Merkle structure, and the registry periodically publishes signed tree heads that allow any third party to verify (a) that a given event appears in the log at a given instant, (b) that history has not been rewritten. The entire log is public and downloadable, with no restricted-access content. Direct consequence: public cryptographic commitments are emitted from the Node phase and bind the registry long-term, independently of the API and the implementation language — hence the requirement of a conservative cryptographic scheme, explicitly portable and compatible with crypto-agility (cf. [Q-LOG-STRUCT], [Q-CRYPTO-AGILITY], and [Q-CRYPTO-IMPL] *defined in `ename-synthesis.md`*). `[settled]`
- **No user metadata in the registry**. The registry stores only the elements strictly necessary for its binding and verification function: `ename`, current public key, history of key transitions, current home operator, lifecycle status. Any profile enrichment (display name, contacts, user information) is the responsibility of operators. This constraint keeps the registry's auditable surface minimal, simplifies the stance toward GDPR erasure requests (structurally impossible to honor on a public append-only log), and reinforces the registry / operators boundary (cf. `ename-synthesis.md` § Mission and boundary). The scope is set at this stage and may be reexamined if a transverse use case requires it. `[working hypothesis]`
- **Event taxonomy and signature scheme**. Each event type has an explicit signature rule:

  | Event type | Signed by | Mechanics |
  |---|---|---|
  | Initial registration (`name#number` + K₀) | Registry operator alone | No prior user key to chain. The residual risk of mis-registration by the operator is detectable by the user (who could not produce valid signed content under the ename). |
  | Key rotation (Kₙ → Kₙ₊₁) | Current user key Kₙ | Cryptographic chaining to the previous control event. Prevents the operator from unilaterally rotating in the user's place. |
  | User-declared revocation | Current user key Kₙ | Or via the recovery flow if the key is inaccessible. |
  | Key recovery | Registry operator alone, explicitly labeled as a recovery event | By definition, the user cannot sign. Public visibility of the event and the procedure framing the recovery replace the cryptographic guarantee. |
  | Deactivation / closure of an ename | Current user key Kₙ | Prevents the operator from closing unilaterally. |
  | Log mechanics (operator signing key rotation, epoch markers, checkpoints) | Registry operator alone | Concerns the structure of the log, not the state of a user ename. |

  Underlying principle: any event that transfers or modifies the **control** of an ename must be cryptographically chained to the previous user key (key chaining mechanics, equivalent to those adopted by DIDs and by the Signal protocol for rotation), or explicitly labeled as a recovery. Any other operation belongs to the log mechanics and may be signed by the registry operator alone. This decision partially addresses [Q-CRYPTO-IMPL] *(defined in `ename-synthesis.md`)* by setting the principle of rotation attestation in the registry; the precise format of signatures and of the reference to the previous entry (hash of the previous entry of the same ename, or index + epoch) remains an implementation detail to be arbitrated together with [Q-LOG-STRUCT]. `[settled]`
- **Key recovery model as seen from the registry**. Any key transition event not chained to a valid user key is encoded as a recovery event, signed by the registry operator, explicitly labeled and publicly visible in the log. The mechanism by which the user established their right to recovery on the operator side (re-KYC, social recovery, cloud-sync via passkey, cf. [Q-KEYREC] *defined in `ename-synthesis.md`*) is external to the registry. Choice motivated by the refusal of the "pure lockout" model (key loss = definitive ename loss), which is socially untenable at the targeted horizon of universal human identity. The residual power of the registry operator is bounded by the public visibility of every recovery and by the procedures framing re-verification (cf. [Q-RECOVERY-PROC]). `[settled in principle]`
- **Initial registration protocol — simple submission of the public key**. At registration, the operator transmits to the registry the public key provided by the user, without any proof-of-key-possession imposed by the registry. The risk that an operator registers an ename with a key it controls rather than the one intended by the user is detectable by the user (who could not sign valid content under their ename) and therefore constitutes a visible attack, not a silent one. Acceptable as a first approach. A proof-of-key-possession may be added later if hardening this bound becomes necessary. `[settled]`
- **Transition monitoring by operators**. The home operator of a user is required, through its accreditation, to monitor the log for the enames it serves and to alert its users in case of an unsolicited transition. Without this monitoring, the public log and the cryptographic chaining only protect retroactively: the silent attack becomes theoretically detectable but not practically detected. The concrete inclusion of this obligation in accreditation requirements is to be finalized with the Ename regulation (cf. [Q-ACCRED-CRITERES] *defined in `ename-synthesis.md`*). `[settled in principle]`
- **`events` table — v1 representation of the log**. As event sourcing makes the log the source of truth and the SQL database its projection (cf. first bullet of this section), the `events` table is the v1 embodiment of the log itself — append-only journal of all registry mutations, source from which the `subjects` and `enames` projections are derived, and precursor of the future cryptographically chained transparency log structure. Five columns (concrete schema in `database/migrations/<ts>_create_events_table.up.sql`):

  - `sequence` (PK, `BIGINT GENERATED ALWAYS AS IDENTITY`): position in the log. Strictly monotonic, allocated by PostgreSQL at INSERT — unambiguous ordering across concurrent backends, which UUIDv7 cannot guarantee at the millisecond granularity. This same column will be the leaf index in the future transparency-log structure (cf. [Q-LOG-STRUCT]).
  - `idempotency_key` (UUIDv7, UNIQUE): client-provided idempotency key — transport metadata, not part of the event's semantic content (cf. dedicated bullet in § Inter-phase invariants). Distinct from the per-HTTP-request `requestId` carried in logs and the `X-Request-Id` response header (server-generated observability concern, never persisted).
  - `kind` (TEXT, CHECK-enumerated): discriminates event types. v1 values: `subject.registered` (a new subject is registered together with its first ename, atomically) and `subject.ename_added` (an additional ename is added to a subject already registered, typically a name change). Distinct kinds rather than a single kind discriminated by payload shape, so the technical taxonomy aligns with the signature semantics anticipated for each operation (cf. *Event taxonomy and signature scheme*). New kinds added via ALTER on the CHECK. **Naming convention**: `<entity>.<verb_past_tense>`, dot-separated, lowercase, snake_case inside each segment. Subject is the canonical namespace for everything that happens to a registered identity (registration, additional enames, future key rotations, recoveries, revocations, deactivations). Past tense follows event-sourcing practice — an event describes a fact that has happened, not an intent.
  - `payload` (JSONB): shaped by domain entities (`subject`, `ename`), never by projection table structure. Always nested by entity block, no duplication of identifiers across blocks. Excludes `idempotency_key` (transport metadata, its own column) and `created_at` (event-level metadata, its own column). The future signed canonical form will be computable from the JSONB if the canonicalization scheme retained for [Q-LOG-STRUCT] is value-defined (e.g. RFC 8785 over JSON values); otherwise a `canonical_content BYTEA` column will be added at signature introduction, applied only to post-signature events.
  - `created_at` (TIMESTAMPTZ): the single timestamp of the event. Projection rows (`subjects.created_at`, `enames.created_at`) inherit from it at replay; never duplicated inside the payload.

  Exception to the doctrine "UUIDv7 PK on every table": the PK is `sequence`, not a UUIDv7. Events are positions in a log, not entities with surrogate identity — UUIDv7 carries no useful property for a log row that `sequence` doesn't carry better (B-tree locality, monotonicity). Cross-reference: § Inter-phase invariants, *Primary key format* bullet, which states the exception. `[settled]`

## Decisions — Node phase

- **Language and runtime**: TypeScript in strict mode (`strict`) supplemented by an opt-in set of options detailed in `backend/tsconfig.json` (notably `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `erasableSyntaxOnly`, `allowUnreachableCode: false`, `noPropertyAccessFromIndexSignature`, `noImplicitOverride`, `noUncheckedSideEffectImports`). Node.js 26 (Active LTS from October 2026), ESM, version enforced by `engines.node` + `engine-strict=true` and by a versioned `mise.toml`. Without this level of discipline, the port to Rust becomes a nightmare on arrival: everything the Rust compiler will require must already be guaranteed on the Node side.

  **Build-less execution pipeline**: Node 24+ runs `.ts` files directly via native type stripping (`node src/server.ts`, no `tsc` emitting JS, no bundler, no third-party loader such as `tsx`). Consequences on the TypeScript config: `noEmit: true`, `allowImportingTsExtensions: true`, `isolatedModules: true`, `verbatimModuleSyntax: true`, imports with explicit `.ts` extensions (`import { foo } from './bar.ts'`). `tsc` remains used as a type-checking safeguard (`npm run typecheck`), without producing any output. `erasableSyntaxOnly` locks this discipline in by forbidding any TS construct that would require a runtime transformation (enums, namespaces with code, parameter properties). A developer who tries to write an `enum` is stopped by typecheck rather than discovering the incompatibility at runtime on Scaleway. `[settled]`
- **Package manager and supply-chain defense**: npm 11.10+, configured via a versioned `.npmrc` with:
  - `min-release-age=3` (3 days — the npm unit is in days, unlike `pnpm` which uses minutes for `minimumReleaseAge`; more conservative cooldown than the pnpm default of 24 h, chosen to absorb slower detections, public holidays and weekends during which community yanking of a compromised package slows down).
  - `ignore-scripts=true` (lifecycle scripts `preinstall`/`install`/`postinstall`/`prepare` globally disabled by default, including for the repo's own scripts).
  - `engine-strict=true` (npm refuses `install` if the active Node version does not match the `engines.node` of `package.json`, pinned to `>=26`). Combined with the `mise.toml` versioned in the backend package, this guarantees that no contributor accidentally uses an incompatible Node version — avoids silent bugs of the kind "the code passes tests on Node 24 but uses a feature only present in 26".
  - Manual allowlist of packages authorized to run their scripts: explicit list in a `rebuild:trusted` script of the repo's `package.json`, in the form `npm rebuild --ignore-scripts=false <pkg1> <pkg2> ...`. Two-step install workflow: `npm install` then `npm run rebuild:trusted`. Any modification of the list goes through code review via the diff of `package.json`. No third-party tool (`@lavamoat/allow-scripts` considered then discarded so as not to introduce an external maintainer at the core of the install security mechanism).
  - `lockfile-lint` in CI to forbid any source other than `registry.npmjs.org` in `package-lock.json` (git URLs, HTTP tarballs, etc.).

  Choice driven by: (a) the will to stay on the default tool of the Node ecosystem to minimize operational surface (one fewer binary, official distribution), (b) a measured bet on the convergence of npm security defaults toward those of pnpm 11 — npm 11.10 has already introduced `--min-release-age` as a flag and hardened `--ignore-scripts`, npm 12 is announced to enable `minimumReleaseAge` by default at 1440 minutes, (c) trivial switching cost toward pnpm if the catch-up does not pan out (regenerating the lockfile, adjusting CI, no impact on application code).

  Explicit trade-offs accepted relative to pnpm 11:
  - No strict structural resolution: phantom deps remain technically accessible (npm hoists to the root of `node_modules/`). Countermeasure: ESLint rule `import/no-extraneous-dependencies` enabled in strict mode, plus writing discipline.
  - No native blocking of exotic sub-dependencies: covered by `lockfile-lint`.
  - No automatic tripwire in case `ignore-scripts` is disarmed: a commit removing the line from `.npmrc` or a misconfigured CI environment would not trigger an install error. Countermeasure: explicit CI check verifying that `.npmrc` contains `ignore-scripts=true` before any `npm install`.
  - Allowlist maintained by hand instead of by a dedicated tool: real friction with every dependency addition requiring a script, but a very explicit review artifact (modification visible in the `package.json` diff) and zero external maintainer added to the trust chain.

  **Reevaluation trigger**: npm 12 release. If npm 12 enables `minimumReleaseAge` by default and hardens the lifecycle-scripts posture as announced, the bet is validated and we stay on npm, lightening `.npmrc` of the defaults now native. If npm 12 ships without these defaults, or if a supply-chain incident not covered by our `.npmrc` happens before, immediate switch to pnpm. `[settled in principle]`
- **Linting and formatting**: Prettier for code formatting, ESLint as a complement for everything Prettier does not cover. **Guiding principle: Prettier and ESLint are complementary and do not duplicate each other.** Prettier keeps a monopoly on the formatting it already handles (whitespace, punctuation, line breaks, line length). ESLint covers what falls outside that scope: (a) classes of runtime bugs that neither `tsc` nor Prettier sees, (b) style or code-organization rules that require more configuration than Prettier offers. No opaque preset (`airbnb`, `standard`, etc.) — every enabled rule must remain individually justifiable. Starting configuration:
  - `@typescript-eslint` with a type-aware parser: `no-floating-promises` (forgotten await on an async call), `no-misused-promises` (async passed where a boolean or void is expected), `await-thenable` (await on a non-Thenable), `require-await` (async without await).
  - `eslint-plugin-import-x`: `no-extraneous-dependencies` (countermeasure to phantom deps, cf. decision on the package manager) and `import-x/order` (organization of imports into configurable groups — builtin, external, parent, sibling). Active fork of `eslint-plugin-import` preferred to the original for: (a) ESLint 10 support (the original caps at 9), (b) lighter architecture (internal Rust resolver, `get-tsconfig` instead of `tsconfig-paths + typescript` as transitives) which reduces the npm dev install surface by roughly half, (c) significantly more active release cadence.
  - `eslint-plugin-unused-imports`: `no-unused-imports` for auto-fixable removal of unused imports (TypeScript strict via `noUnusedLocals` already detects them at compile time, but does not remove them automatically).
  - Everything else falling under formatting is left to Prettier; everything else falling under dead-code detection outside imports is left to TypeScript strict flags (`noUnusedLocals`, `noUnusedParameters`, `noImplicitReturns`, etc.).

  Minimal Prettier configuration (`.prettierrc`): three options set explicitly, the rest left to the Prettier 3 default which is effectively the ecosystem standard.
  - `singleQuote: true` — dominant convention in modern TS, minimizes friction with external snippets (docs, Stack Overflow, etc.).
  - `printWidth: 100` — comfortable on a modern screen, wider than the default 80 without falling into lines too long to scan.
  - `endOfLine: 'lf'` — Prettier default already, set explicitly to defend against a Windows checkout with `core.autocrlf=true` that would produce local CRLFs and "entire file changed" diffs.

  `prettier-plugin-organize-imports` considered then discarded: functional and integrated into the formatter, but the import order is not configurable (frozen by the TypeScript Language Service). Preference given to the pair `import-x/order` + `eslint-plugin-unused-imports` to keep explicit control over import groups and their order, at the cost of two additional ESLint plugins.

  Choice driven by: (a) honest recognition that TypeScript strict, even at its highest level, does not cover asynchronous patterns — an unawaited `Promise` is statically valid (the type `Promise<T>` is acceptable as a statement) but silently causes unhandled rejections and race conditions at runtime; a class of bug particularly intolerable for a registry backend where every write is an immutable event in the log; (b) the will to keep a list of enabled rules each individually justifiable rather than an opaque preset; (c) acceptance that the list will grow over time as soon as a concrete case justifies the addition — ESLint is treated as a tool open to extension, not as a stack frozen to the minimum vital.

  **Biome considered then discarded as first choice**: single binary aligned with the preference for minimalism and the Rust horizon, but its type-aware rules (introduced in Biome 2.x in 2025) remain less mature than those of typescript-eslint on critical asynchronous patterns. To be reevaluated if Biome consolidates its coverage, or simply abandoned during the Rust port (where the question of a JS linter disappears). `[settled]`
- **HTTP framework**: Hono + `@hono/zod-openapi` (Zod v4 compatible since PR #1223). Chosen for: typed function handlers, composable middleware, code-first OpenAPI generation philosophically close to utoipa, native alignment with Zod. Express and NestJS excluded (paradigms anti-portable to axum). Fastify remains a reasonable fallback if Hono poses a stability problem on pure Node (`@hono/zod-openapi` remains younger than the Hono core). `[settled]`
- **SQL access**: `pg` (node-postgres) with parameterized raw SQL, row parsing via Zod schemas at the boundaries. Chosen for: stable continuous maintenance since 2010, `$1` placeholder syntax directly portable to sqlx, structurally large user base (underlying driver of Prisma/Drizzle/Kysely, hence durable maintenance pressure). `postgres.js` considered then discarded due to the single-maintainer profile with a ~18-month gap observed in 2024-2025. Safety net missing compared to sqlx: no compile-time check of queries against the DB schema — mitigated by Zod at the boundaries and systematic integration tests against real PostgreSQL. `[settled]`
- **DB access helpers**: all SQL goes through two minimalist helpers — `queryRows(db, sql, params, schema)` for individual queries, `withTransaction(pool, fn, logger)` for atomic blocks. The first argument `db` is typed `Pool | PoolClient` (both expose the same `.query` method), so the same helper serves indifferently outside and inside a transaction, with no separate helper. `queryRows` applies `camelize()` to each row before Zod validation, which allows Service Layer schemas to be defined in camelCase and business logic to manipulate objects conforming to the JS convention, without ever seeing snake_case DB. No conversion in the reverse direction: `pg` passes parameters positionally (`$1`, `$2`), column names appear only in the SQL text. The pattern carries directly over to Rust via `&Pool` / `&mut Transaction` in `sqlx`, without case conversion (cf. inter-phase divergence on the application convention). Cases that fall outside this pair (`LISTEN`/`NOTIFY`, `COPY FROM`/`COPY TO`, streamed cursors) bypass by nature the row→Zod pattern and will have their own helpers the day they appear — not required for v1.

  **Cleanup must not mask the original error.** Any `ROLLBACK` or `ROLLBACK TO SAVEPOINT` issued from inside a `catch` block must itself be wrapped in `try/catch`. A rollback failure (typically a dead connection: network drop, server-side idle-in-transaction kill, or a `COMMIT` that itself rejected) is incidental — the original error is what the operator needs to see. The rollback failure goes to the logger with full pino context (`{ err: rollbackError }`); the original error is re-thrown unchanged. `withTransaction` already follows this pattern; any future code using SAVEPOINTs or manual transaction management must apply the same discipline. The Rust phase via `sqlx` handles this implicitly through `Drop` on `Transaction`, but the discipline of preserving the original error on cleanup failure remains the same. `[settled]`
- **PG pool config**: a single `pg.Pool` instantiated as a module singleton in the Service Layer (`src/database/pool.ts`), connected via `config.databaseUrl` (resolved to `DATABASE_URL` or `TEST_DATABASE_URL` depending on `NODE_ENV` in `src/config.ts`). Hard-coded parameters, identical in dev and prod: `statement_timeout: 5_000` ms, `query_timeout: 10_000` ms, `application_name: 'ename-backend'`, `max: 10`, `connectionTimeoutMillis: 5_000`, `idleTimeoutMillis: 10_000`. The **`statement_timeout` of 5 s is not an operational detail**: it is an implicit SLA on query latency that constrains index design and query writing on the Service Layer side — any query that exceeds it signals either a bug, or a legitimate case (admin batch, ad-hoc operation) that must explicitly go through a `SET LOCAL statement_timeout` in the transaction concerned. Value identical between dev and prod by deliberate choice: slow queries must surface in dev, not be discovered in prod. `application_name` is set hard (the service does not change name depending on the env) so it can be found in `pg_stat_activity` and Scaleway logs. `statement_timeout` is passed via the driver's startup parameters (first-class option of `pg.Pool`), never via `SET` post-connection — required by Scaleway Serverless SQL's transaction-mode PgBouncer pooler, cf. dedicated decision. All these levers transpose one-for-one to `sqlx::PoolOptions` on the Rust phase side. `[settled]`
- **Runtime validation**: Zod v4 everywhere at the boundaries (HTTP input, HTTP output, DB rows). Schemas defined at the top level of modules, never dynamically rebuilt (Zod v4's JIT cache depends on schema identity — a schema recreated at every request loses ~100× in throughput). `[settled]`
- **Configuration loading**: environment variables parsed and validated via a Zod schema centralized in `src/config.ts`, exposed as a frozen module singleton (`Object.freeze`). Validation failure → immediate `process.exit(1)` with a readable message (`z.prettifyError`), rather than starting up with invalid config that would produce cascading bugs later. In local dev, `.env` loaded via `node --env-file-if-exists=.env` (Node built-in since 22.7, no `dotenv` dependency). In prod, env vars come from the Scaleway platform. `.env.example` versioned documents the expected variables. No `process.env.X` beyond `src/config.ts` — usage sites import typed `config.X`. `[settled]`
- **Logger**: `pino` as application logger, module singleton in `src/logger.ts`, level controllable via `LOG_LEVEL` in the config. **JSON output in all environments** including local dev (no `pino-pretty` transport by default). Choice motivated: forces familiarity with the production log format from dev, avoids surprises at the first incident in prod. For a human terminal, `... | jq` remains the reading tool. Pino convention preserved for errors (`logger.error({ err: error }, '...')` engages `stdSerializers.err` which serializes stack + cause — exception documented in the "Naming conventions" bullet). The HTTP middleware for request logging (server-generated `requestId` UUIDv7 + contextualized Pino child logger, exposed via Hono `Variables` as `c.var.requestId` and `c.var.logger`, plus an `X-Request-Id` response header) was wired with the first non-trivial endpoint (`POST /api/v1/subjects`). Services that need a request-correlated logger receive it as an explicit argument in their `context` parameter (`registerSubject(input, { logger })`) — no AsyncLocalStorage, no implicit propagation, consistent with the discipline that the Service Layer never touches the Hono `Context`. `[settled]`
- **Zod schema organization**: two watertight layers aligned with the application architecture (cf. inter-phase invariants), without cross-imports. Schemas live **by default in the same file as their consumer** (route handler on the API side, service function on the Service Layer side). Extraction to a dedicated file `src/api/schemas/<resource>.ts` or `src/services/schemas/<resource>.ts` as soon as one of these two conditions appears: (a) the schema is consumed by multiple files, (b) the consumer file becomes too dense to remain readable. Same switching logic as module splitting by use case: inline as long as it's small, dedicated folder when it grows.

  Characteristics specific to each layer, regardless of location (inline or extracted):
  - **Services Layer**: DB rows and domain objects, without OpenAPI annotations, native types (`z.date()`, `Date`...).
  - **API Layer**: types exposed over HTTP, `.openapi()` annotations, reusable refs via `.openapi('Name')`, serialized formats (`z.iso.datetime()`, etc.).
  - Composition by field blocks (`Identifiable`, `Timestamps*`, `PersonIdentity`, etc.) **intra-layer only**. Crossing between layers goes through explicit mapping functions (`personRowToResponse`), not through chained `.transform()` that mix levels. This pattern reproduces the `sqlx::FromRow` vs `serde::Serialize + utoipa::ToSchema` separation of the Rust phase, and ports as an `impl From<PersonRow> for PersonResponse`. `[settled]`
- **DB migrations**: home-grown runner (~100 lines of TS in `backend/scripts/migrate.ts`), migrations in pure SQL in the `database/migrations/<unix_ts>_<name>.up.sql` + `.down.sql` format. Chosen for maximum portability: this is exactly the layout that `sqlx-cli` reads, so the `database/migrations/` folder transfers to the Rust phase without any transformation. Third-party tools considered and discarded: `dbmate` (bundles up/down in a single file with markers, which would impose a splitting script at port time), `node-pg-migrate` (second-class SQL mode, maintenance slowed since late 2023), `postgrator` (single-maintainer, `001.do.sql` naming to be renamed), `graphile-migrate` (roll-forward philosophy incompatible with the sqlx model). Runner invariants: `pg_advisory_lock` around the run, `schema_migrations(version, name, hash, applied_at)` table with SHA-256 of the content to detect silent post-merge edits, transaction per migration unless the header `-- migrate:no-transaction`, lexicographic sort, single connection. No `down` command exposed — `.down.sql` files exist for sqlx parity and manual rollback, never as a production command. Schema dumped via `pg_dump --schema-only` into `database/schema.sql` (versioned). `[settled]`
- **Architectural discipline**: pure functions at both levels — API Layer handlers as Service Layer functions. No DI framework, no runtime decorators, no classes with hidden state. Each Node pattern retained must have an identifiable axum equivalent.

  **Per-layer visibility rule**: a resource appears only at the layer that consumes it. The PG pool, SQL helpers and transactions live in the Service Layer and stay there; the API Layer never sees them, it translates HTTP ↔ service calls. Symmetrically, the Hono `Context` carries only values that the API Layer itself needs at request time.

  Dependency propagation then follows three regimes:
  - **Stateless functions** (pure validators, business rules without I/O, computation helpers): direct import, signature `(input) → output`. No injection — there's nothing to inject.
  - **Process-lifetime resources** (configuration loaded at boot, root logger, PG pool): module singletons initialized at import (`export const config = loadConfig()`, `export const pool = createPool(config)`), hosted in the layer that consumes them and imported directly by usage sites. The PG pool lives in a Service Layer module and remains invisible to the API Layer; a shared root logger lives in a common module. Not hidden state in the problematic sense as long as construction is explicit, the singleton is frozen after init, and the import is visible at the top of the file. Rust equivalent: `OnceLock` / `LazyLock` in the hosting module — **not** `axum::State<T>`, which would be an unnecessary detour for resources that handlers don't touch.
  - **Request-scoped values consumed by the API Layer** (request ID, contextualized child logger, authenticated identity resolved by a middleware): carried by the Hono `Context` via `c.var.*`, populated by a dedicated middleware. Native use case for typed `Variables` (`OpenAPIHono<{ Variables: ... }>`). Rust equivalent: `axum::Extension<T>` set by `middleware::from_fn`, or dedicated typed extractor.

  Two cases of cross-layer circulation follow:
  - A request-scoped value that the Service Layer needs (typically an authenticated identity to be transmitted to the service) is extracted from the `Context` by the API handler and passed as an explicit argument to the service function called. The Service Layer never sees the Hono `Context`.
  - A request-scoped value originating in the Service Layer (a `PoolClient` acquired for a transaction, for example) does not bubble up to the Hono `Context`: it flows as an explicit argument between the service functions that need it, in accordance with the decision on multi-table transactions.

  **Domain errors and HTTP status mapping**: the Service Layer throws semantic error classes — `DomainError` and its subclasses `ValidationError`, `IdempotencyConflictError` — defined in `src/services/errors.ts`. Services know nothing about HTTP status codes. The mapping to HTTP responses lives in a single place: the API Layer's `app.onError` handler (`src/api/index.ts`), which maps `ValidationError` → 422, `IdempotencyConflictError` → 409, anything else → 500. Adding a new domain error and its status is a one-touch operation in the `onError` table. Error messages on `DomainError` subclasses are written for the **client**: generic, actionable, no internal vocabulary leak (no event kinds, column names, SQL codes, or arithmetic in the public `detail` string). Technical specifics — which event kind was actually stored, which field differed in a conflict, the arithmetic of an overflow — are logged separately via the service's `logger` with full pino context, correlatable by `requestId`. The Rust phase will use an `enum AppError` with an `IntoResponse` impl carrying the same mapping table; the discipline of "domain knows nothing about HTTP" carries over verbatim. `[settled]`
- **Naming conventions**: explicit, fully-spelled names, no abbreviations (`context` rather than `c`, `error` rather than `err`, `request` rather than `req`, `response` rather than `res`, etc.), even when the host framework's convention (Hono, Express, etc.) proposes abbreviations in its examples. Justification: multi-century horizon and future port to Rust where JS framework conventions no longer apply — the future reader is not necessarily steeped in the codes of the current stack, and an explicit name remains readable without the framework's context. Tolerated exceptions: `id`; acronyms (`url`, `http`, `json`); iteration variable `i` in a short loop; conventional keys passed to a library that auto-applies a behavior on that name (typically `logger.error({ err: error }, ...)` on the pino side — the variable name remains `error`, but the key passed to pino remains `err` to engage `stdSerializers.err`). No automatic enforcement on the ESLint side (the available rules — `id-length`, `id-match` — are too coarse to express this nuance), upheld via code review. `[settled]`
- **Function form**: `function` declaration for top-level exported functions whose signature is explicit (`export function checkHealth(): boolean { ... }`). The `const fn = (...) => ...` form is reserved for handlers and callbacks where the type annotation lives on the binding via a type helper provided by the framework (typically `export const healthHandler: RouteHandler<typeof healthRoute> = (context) => ...`, where `RouteHandler<...>` infers the type of `context` from the route definition — switching to `function` would require manually annotating every parameter and the return value, duplicating the work of the type helper). Arrow also for all inline callbacks (passed to a middleware, to `.map`, to `setTimeout`, etc.). Justification for favoring `function` at top level: immediate visual signal ("this is a function" read without having to reach `=>`), hoisting that simplifies intra-module dependencies, symmetry with the Rust target where `pub fn` is the canonical form. `[settled]`
- **Tests**: `node:test` (built-in Node 22+), systematic integration against real PostgreSQL (local Docker cluster for dev, dedicated Serverless SQL instance in CI), no DB mocks. `ename_test` database distinct from `ename_dev` in the same local cluster — separation guarded by two explicit URLs (`DATABASE_URL` vs `TEST_DATABASE_URL`) **and** by a `NODE_ENV !== 'test'` safeguard in the reset helper, which refuses to truncate if the environment is not explicitly "test". **Isolation between tests via `TRUNCATE ... RESTART IDENTITY CASCADE`** on all tables of the `public` schema (except `schema_migrations`), executed in `beforeEach` via a `resetTestDb(pool)` helper that discovers tables dynamically via `pg_tables` (no hand-maintained list). The classic alternative "`BEGIN`/`ROLLBACK` per test" is **excluded** because it is incompatible with `withTransaction`: the tested code that itself opens a transaction would end up in a nested SAVEPOINT, whose isolation semantics differ from those of a top-level transaction — a test would pass locally and critical transactional behavior would remain uncovered. **Sequential file execution** (`node --test --test-concurrency=1`): `node:test` defaults to running test files in parallel, which is incompatible with the shared-DB + `TRUNCATE`-per-test isolation strategy — two test files truncating concurrently corrupt each other's state mid-test. The cost is real (current suite ~21s sequential vs ~7s parallel) and worth accepting as long as integration tests dominate. The Rust equivalent (`sqlx::test`) sidesteps this by giving each test its own ephemeral database; we'll converge on the same model when test count makes the sequential cost painful. Integration tests are conceptually portable to Rust (same schema, same semantic assertions, same reproducible isolation strategy via an equivalent helper or `sqlx::test` modulo configuration); Node-specific mocks are throwaway. `[settled]`

## Decisions — Rust phase (target)

- **Backend stack**: Rust with `axum` for the HTTP layer and `sqlx` for SQL access. Chosen for memory safety, predictable performance and the maturity of the Rust ecosystem for long-running network services. `[settled]`
- **Code-first OpenAPI generation**: `utoipa`, with a CI safeguard verifying non-regression of the generated spec against the canonical spec (cf. invariant decision below). `[settled]`
- **Migrations**: `sqlx-cli`, reading the SQL files produced during the Node phase via `dbmate` (compatible format, transferred as-is). `[settled]`

## Decisions — inter-phase invariants

- **Two-layer application architecture**: the backend is organized in two conceptual layers, with no dedicated persistence layer and no separate Domain layer.
  - **API Layer** (`src/api/`): the service's HTTP surface — routing, input and output validation (Zod on the Node side, serde + utoipa on the Rust side), serialization, return codes. Implements no business logic, delegates entirely to the Service layer.
  - **Service Layer** (`src/services/`): carries all business logic and accesses the database directly (no Repository pattern). Within the layer, conventional separation between **pure business-rule functions** (invariants, validations, computations — testable without DB) and **use-case functions** (orchestration: validate via the pure functions, read/write in DB, return). Splitting by use case rather than by entity as soon as a module exceeds half a dozen functions (vertical slices like `services/person/create.ts`, not a god-module `services/person.ts`). **Service modules are named in singular** (`ename.ts`, `subject.ts`, …): a service module groups operations on the entity concept, it does not itself hold a collection — the plural is reserved for SQL tables (which contain a collection) and REST routes (which address a collection). The asymmetry is deliberate.
  - Justifications for rejecting the classic Repository pattern: (a) no DB swap planned (Postgres in both phases); (b) integration tests against real PostgreSQL — no mocks to wire onto an interface; (c) mostly CRUD-shaped domain; (d) idiomatic style of the target `axum`+`sqlx` which pushes exactly toward function modules calling `sqlx::query!` directly; (e) consistent with the discipline "no DI, no classes with hidden state". `[settled]`
- **Multi-table transactions**: managed explicitly by the Service use case that needs them — manual `BEGIN`/`COMMIT` via `pool.connect()` on the Node side, `sqlx::Transaction` passed as an argument on the Rust side. No transparent transactional middleware, no implicit "every handler opens a transaction" wrapper. Choice motivated by: (a) making the transactional perimeter explicit at the point where it is decided, (b) direct Node → Rust portability without rewriting the propagation model. `[settled]`
- **Public API contract in OpenAPI 3.1**: the contract has two representations whose roles are distinct and deliberate.
  - **Canonical representation** — versioned file at `backend/openapi.json` (root of the backend package, outside the source folder to distinguish the contract from its implementation `backend/src/api/`). JSON format rather than YAML — `oasdiff`, `@hono/zod-openapi` and `utoipa` produce and consume both indifferently, the choice is cosmetic on the tooling side. Produced by `npm run openapi:generate`, committed in git, serves as an audit trail of contract evolutions. Target consumers off-runtime: SDK generators, static documentation, CI safeguard.
  - **Runtime representation** — served over HTTP at `/api/v{N}/openapi.json` by each version sub-app. Generated at each request from the running Hono app, hence **always in sync with the code that runs**, without any manual generation step. Target HTTP consumers: interactive viewer/runner (Scalar embedded at `/api/v{N}/docs`), human inspection via `curl | jq`, dynamic tools.

  Both representations are produced by the same `getOpenAPI31Document()` call — possible divergence only between a route modification and regeneration of the canonical. This is precisely what a CI safeguard via `oasdiff` (language-agnostic Go binary) will detect, failing the build if the committed canonical no longer matches what the code produces. Language-independent source of truth: the backend (Node then Rust) generates its own spec from annotated code (`@hono/zod-openapi` then `utoipa`), and the Rust port naturally inherits the same contract. Global goal: no silent drift between implementation and public contract. `[settled]`
- **Route versioning via sub-app mounted under prefix**: each major version of the public API is carried by a distinct HTTP instance (`OpenAPIHono` on the Node side, `Router` on the Rust side), mounted at top level via `app.route('/api/v1', api)` on the Node side or `Router::nest('/api/v1', v1_router)` on the Rust side. Practical consequences:
  - **v1/v2 cohabitation** during a migration of external consumers: an additional mount at the top level, v1 remains intact.
  - **Routes defined without a version prefix** in their files (the prefix is applied at mount → single source of truth for the version of a route).
  - **Spec and interactive UI per version**: each sub-app exposes its own `/api/v{N}/openapi.json` and its own `/api/v{N}/docs` (cf. OpenAPI bullet above for the role of the runtime spec).

  Discarded alternatives: inline prefix in the `path` of each route (disperses version information, friction at the move to v2); `basePath` at the top-level app (forces the prefix on all routes including any non-versioned endpoints at the root). `[settled]`
- **Separation of assembly entry point / runtime entry point**: the code that **assembles the HTTP application** (sub-app composition, route registration, middleware configuration, spec exposure) lives in a module **with no side effects**, importable by integration tests that drive the app via `app.fetch(request)` without opening a port. The code that **runs the application on the target runtime** (listen adapter, POSIX signal handling, connection draining, graceful shutdown with timeout) lives in a separate module that imports the first and adds runtime concerns.

  Node phase: `src/index.ts` (assembly, exports `app`) + `src/server.ts` (runtime via `@hono/node-server`, handles `SIGTERM`/`SIGINT` and draining with a hard timeout of 10 seconds above, clean exit).
  Rust phase: `src/lib.rs` or `src/app.rs` (assembly of the axum `Router`) + `src/main.rs` (runtime via `tokio::main` + `axum::serve`).

  Benefits: (a) trivial integration tests without ephemeral ports or network mocks, (b) clear conceptual boundary between "what the app does" and "how it is run", (c) only the runtime module changes upon a change of adapter or deployment model. `[settled]`
- **Hosting**: Scaleway, in serverless mode — Serverless Container for the HTTP backend (language-agnostic, Node and Rust supported the same way), Serverless SQL for the database. Motivations: sovereignty (European infrastructure operator), operational simplicity at startup, consistency with the association's jurisdiction. Reservation about the Node phase: the cold start of a Node container is noticeably higher than in Rust; plan for a min instance > 0 as soon as there is regular traffic. `[settled]`
- **Scaleway Serverless SQL constraints**: Serverless SQL places a **PgBouncer in transaction mode** in front of each database, plus a series of PostgreSQL features disabled or weakened. These constraints are **not reproducible locally** (the PG 16 of the dev Docker Compose runs without a pooler) — the discipline is to avoid them in the code, not to try to emulate them. To respect by construction:
  - **`SET` / `RESET` / `DISCARD ALL` unreliable** on the session side: the pooler multiplexes logical connections onto physical backends between transactions, so any session-scoped state may jump from one request to the next. `statement_timeout` and other equivalent parameters must be set via the driver's startup parameters (`statement_timeout` option of `pg.Pool` on the Node side, equivalent in the connection URL or `after_connect` on the `sqlx` side), never via `SET` post-connection.
  - **`LISTEN`/`NOTIFY` allowed but with no delivery guarantee**: excluded as a reliable notification mechanism. Any need for asynchronous messaging will go through a dedicated broker (to be arbitrated the day the case arises).
  - **Advisory locks without guarantee**: usable only by tools that run off the prod path (the migration runner uses one, it's acceptable because the tool runs in CI or at instance boot and an accidental double-execution simply fails cleanly). Forbidden as an application coordination primitive.
  - **No `PREPARE TRANSACTION`** (two-phase commit), **no session temporary tables**, **no `REFRESH MATERIALIZED VIEW CONCURRENTLY`**, **no security labels**.
  - **DDL on roles and databases via Scaleway console/API only**, not via SQL — any automation around the databases (provisioning, ephemeral environments) goes through the Scaleway API.
  - **Query size capped at 1 MB**, short transactions expected ("a few seconds" per Scaleway doc) — consistent with the `statement_timeout` 5 s set on the pool side.
  - **~40 PostgreSQL extensions supported** (`pgvector`, `postgis`, `timescaledb`, `pg_cron`, `pgcrypto`, `pg_stat_statements`, etc.) — any other extension is excluded from the architecture by default, to be explicitly verified against the up-to-date list before any design commitment that would depend on it.

  List to confirm periodically against the official doc (`scaleway.com/en/docs/serverless-sql-databases/reference-content/known-differences/` and the supported extensions page): Scaleway evolves the product surface, and the tech doc will not be authoritative on these details beyond a few months. `[settled]`
- **Primary key format**: UUIDv7 (RFC 9562) for the primary keys of all tables in the schema. Storage in 16 bytes via PostgreSQL's native `uuid` type, application-side generation (`uuid` package on the Node side with `v7()`, `uuid` crate on the Rust side with `Uuid::now_v7()` — strictly identical binary formats) rather than by the database — portable across PostgreSQL versions, independent of the native `uuidv7()` function which only arrives in PG 18. Chosen for: (a) B-tree index locality guaranteed by the time prefix (~3× faster on scan, ~25% less index at large volume compared to a random id); (b) open standard ratified in 2024, which aligns the project with the ecosystem convergence (Snowflake, ULID, KSUID standardized as RFCs) rather than on a proprietary format; (c) forward-compatibility with horizontal sharding by hash (Citus or equivalent) should evolution require it. Question of public exposure of these ids decided separately (cf. [Q-ID-PUBLIC]). **Exception for log tables** (currently `events`, future log-mechanics tables): the primary key is `BIGINT GENERATED ALWAYS AS IDENTITY` representing position in the log, not UUIDv7 — log entries are positions, not entities. See § *Registry architecture as a verifiable event log* for the rationale on `events`.

  **Validation and exposure format**: the strict pattern `^[0-9a-f]{8}-[0-9a-f]{4}-7[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$` — case-sensitive lowercase per RFC 9562 §4 canonical form, version nibble 7, RFC 4122 variant bits 10 — is exported once from `src/uuid.ts` and applied at **every** UUIDv7 boundary: request inputs (`idempotencyKey`), response fields (`subject.id`, `ename.id`, `requestId` extension in Problem Details), `X-Request-Id` response header, and persisted payload validation on replay. Case-sensitive on input matches what we emit on output; tolerating uppercase would create asymmetric strictness. The regex is declared without flags (`/i` excluded) so that `Zod.regex(...).toString()` does not leak flag delimiters into the OpenAPI `pattern` field (a flagged regex produced `"...$/i"` in the generated JSON Schema — malformed and silently broken for SDK generators). `[settled]`
- **SQL naming convention**: lowercase snake_case for all identifiers (tables, columns, indexes, constraints). Aligned with PostgreSQL's automatic folding of unquoted identifiers and with the idiomatic Rust convention on the Phase 2 side. On the Phase Node side, conversion to camelCase happens at the DB output point (cf. "DB access helpers" decision, Phase Node). SQL reserved words avoided even when PostgreSQL accepts them (`account` rather than `user`, `kind` rather than `type`, etc.) — including for SQL standard reserved words that are not reserved by PG, to remain portable and readable. **Tables in plural, columns in singular**: the table represents a collection (`subjects`, `enames`), each column an individual attribute (`id`, `name_part`, `kind`). **Foreign key pattern**: `<singular_table>_id` references `<plural_table>.id` — for example `subject_id` references `subjects.id`. The asymmetry is intentional and carries a reading signal: an FK designates *one* element in *the corresponding collection*. `[settled]`
- **SQL schema discipline — projections of an event log**: direct consequences of the foundational decision "the log is the source of truth, the SQL database is a projection" (cf. § Architecture). The set applies to all tables of the registry, in both phases.
  - **`created_at TIMESTAMPTZ NOT NULL` without `DEFAULT now()`**. The value is provided by the application from the timestamp of the corresponding event in the log, not generated by the DB server. A `DEFAULT now()` would make the projection non-deterministic — two replays of the same log would produce different `created_at` values, contradicting the property of full reconstructibility by replay. **Service-side corollary**: a use case that writes to multiple tables captures `const createdAt = new Date()` **once** at the start of the function and propagates the same value to every `INSERT` (subjects, enames, events, …) and to the event payload. The three (or more) rows written by a single event therefore share an exact, byte-identical timestamp — a property the integration tests assert directly and that a reader can rely on when chasing "which event produced this row" by timestamp equality.
  - **No `DEFAULT` on `id`**. UUIDv7s are generated by the application (cf. "Primary key format" bullet), never by PostgreSQL. An `INSERT` without `id` must fail clearly on the `NOT NULL` violation rather than masking an oversight bug with a silently generated value.
  - **No `updated_at` column in the projections**. The model is append-only: successive modifications (key transitions, operator transfers, revocations, etc.) are modeled by new rows in dedicated history tables, never by `UPDATE` on an existing row. An `updated_at` column would be either redundant with history, or divergent — in both cases a trap.
  - **Application-side validation / PostgreSQL `CHECK` boundary**. Invariants likely to evolve with the public format (allowed character class, fine structural rules of an identifier, etc.) live only in the Zod schemas on the Node side (and their serde/validator equivalents on the Rust side). PostgreSQL `CHECK` constraints encode only invariants that will survive all anticipable format evolutions: min/max length, absolute numeric bounds, the broadest character class ever envisaged. This boundary prevents a minor format evolution (allowing digits for organization enames, for example) from triggering a costly DDL migration.
  - **Manual index on foreign key columns**. PostgreSQL automatically creates an index for `PRIMARY KEY` and `UNIQUE`, but **not** for `FOREIGN KEY`. To be created explicitly (`CREATE INDEX <table>_<column>_idx ON <table> (<column>)`) as soon as an "all Xs of a Y" access pattern is plausible — almost always the case, and the cost of an excess index remains lower than the cost of a seq scan on a large table.
  - **Constraint naming**: `PRIMARY KEY`, `FOREIGN KEY` and `UNIQUE` left to PostgreSQL auto-naming — the generated names are predictable and useful in error messages (`subjects_pkey`, `enames_subject_id_fkey`, `enames_name_part_number_part_key`). `CHECK` constraints are **explicitly named** because PG auto-naming calls them `<table>_check`, `<table>_check1`, etc., which makes violations illegible in logs and complicates diagnosis. `[settled]`
- **Public API serialization convention**: camelCase for JSON keys in payloads (requests and responses). Choice carried by the canonical OpenAPI contract, identical in both phases. On the Node phase side, natural alignment with the internal JS convention — the API layer schemas expose camelCase domain objects directly. On the Rust phase side, where internal structs are in snake_case, `*Response` structs carry `#[serde(rename_all = "camelCase")]` to produce the same public surface. `[settled]`
- **Application naming convention — assumed inter-phase divergence**: the naming convention of objects internal to the Service layer differs between the two phases. Node phase: camelCase (JS convention, conversion applied at the DB output point by `queryRows`). Rust phase: snake_case (idiomatic Rust convention, natural alignment with column names, no conversion). Divergence strictly confined within the Service layer; the public OpenAPI contract is fixed in camelCase (cf. dedicated decision) and remains identical in both phases. The `rowToDomain` mapping function exists in Node and disappears in Rust; the `domainToResponse` function (or its `impl From` equivalent) exists in both phases. `[settled]`
- **Numeric log fields — cross-language mapping**: BIGINT columns that carry log positions or related counters (currently `events.sequence`, future leaf indexes, epoch markers, etc.) follow a 2^53-safe convention end-to-end. PostgreSQL `BIGINT` → `bigint` (native) on the Node phase, `i64` on the Rust phase, **serialized as `string`** in the public JSON API (OpenAPI schema `type: "string", pattern: "^[0-9]+$"`). Justification: JavaScript `Number` loses integer precision beyond 2^53 ≈ 9 × 10^15, and the multi-century horizon of the log makes this a real eventual concern; exposing in string at the JSON boundary preserves precision for all clients regardless of language and locks the convention before any external client depends on an integer form. The convention applies uniformly to every such field added later. **Scope**: this rule covers fields whose value could grow without an a priori bound on the multi-century horizon (log positions, leaf indices, epoch counters). BIGINT columns with an explicit, narrow bound that fits in 2^53 (e.g. `enames.number_part`, capped at 12 digits = 10^12 ≪ 2^53) are NOT subject to this rule and are serialized as JSON `integer` — JS `Number` handles them losslessly, and `string` would add friction for no gain. The distinction is "unbounded log mechanics" vs "bounded domain counter". `[settled]`
- **API contract — client-provided idempotency key**: every write endpoint accepts an `idempotencyKey` field in the JSON body — UUIDv7, mandatory. The client guarantees uniqueness; retries of the same logical operation reuse the same value. The server guarantees that an `idempotencyKey` already processed will never trigger a second execution — the prior response is returned instead. Enforced at the database level by the `events.idempotency_key UNIQUE` constraint, so the property holds under concurrent backends and across crash-restart. Carried **in the body** (not in an HTTP header such as `Idempotency-Key`) by deliberate choice: the field will be covered by the future operator signature on the request payload, alongside the rest of the event content. If the same `idempotencyKey` is replayed with a **different** body, the server returns `409 Conflict` rather than silently returning the prior response — protects against client bugs that recycle keys across distinct operations. Scope of uniqueness is global in v1 and will become `(operator_id, idempotency_key)` when operator identification arrives — note that per-operator scoping is required for **security isolation** between operators (preventing one operator from observing or denying another's responses by guessing or replaying its idempotency keys), not merely for collision avoidance. The migration will be non-trivial. Naming note: `idempotencyKey` (body, persistent, contract) is strictly distinct from `requestId` (HTTP-level observability id generated server-side, ephemeral, carried in logs and the `X-Request-Id` response header). The two concepts must never share a name in the codebase. `[settled]`
- **Service-side idempotency algorithm**: each idempotent write use case follows the same four-step pattern, applied uniformly across all current and future write endpoints.

  1. **Preliminary `SELECT` on `events.idempotency_key`, *outside* the transaction.** If found, reconcile from the persisted payload immediately — return the prior result (replay, 201) or throw `IdempotencyConflictError` (409). A point lookup on the UNIQUE index is sub-millisecond; doing it before opening the transaction avoids wasted work (subject + ename INSERTs that would have to be rolled back) on legitimate replays.
  2. **Open the transaction; perform the entity INSERTs.** Allocate any server-generated values (UUIDs, sequenced counters) inside the transaction, capture `createdAt` once before opening it (cf. `created_at` corollary in § SQL schema discipline).
  3. **Final `INSERT events` inside the transaction.** On `23505` over `events_<scope>_idempotency_key_key` (currently `events_idempotency_key_key`), the row was inserted by a concurrent backend that won the race between step 1 and now — rollback the whole transaction and re-`SELECT` the winner's row to reconcile. This race-recovery path is unavoidable as long as step 1 is outside the transaction; the cost of avoiding it (advisory locks, larger transaction span) is worse than the cost of handling it.
  4. **Body equality on reconciliation uses structural deep equality** (`node:util.isDeepStrictEqual` in the Node phase) between the stored payload and a reconstruction of what the current input would have produced — re-using the server-allocated fields from the existing payload on the reconstructed side. Field-by-field comparison (`payload.x === input.x && payload.y === input.y && …`) is explicitly **rejected**: a whitelist of compared fields silently violates the idempotency contract the day a new input field is added without updating the comparison. With structural equality, any new input field automatically participates in the comparison; the only list to maintain is the small set of server-allocated fields, which is small and visible.

  Rust phase: same algorithm, with `sqlx::Transaction` for step 2, a typed error enum disambiguating the `23505` constraint name for step 3, and `PartialEq` derived on the reconstructed payload struct for step 4 — semantics preserved, mechanics adapted. `[settled]`
- **Sequential counter scoped to a group**: when a row must carry a numeric counter unique within a group (e.g. `enames.number_part` scoped by `name_part`; future similar patterns), allocation is done atomically inside the `INSERT` via `SELECT COALESCE(MAX(<counter>), 0) + 1 FROM <table> WHERE <group> = $X`, with a `UNIQUE (<group>, <counter>)` constraint as the race guard. Concurrent allocators can read the same MAX and try to insert the same counter value — the second one fails with `23505`, the application retries under a `SAVEPOINT` so the surrounding transaction's earlier work survives. Retry budget bounded (currently 20 attempts), beyond which the request fails loud (500); the client may then retry the whole operation with a fresh `idempotencyKey`.

  Discarded alternatives: a dedicated counter table (`<group>_counters(<group>, next_value)`) with row-level locking — adds a table that must itself be projected from the event log, for no observed benefit at v1 contention levels; PostgreSQL advisory locks — excluded by Scaleway Serverless SQL (cf. dedicated bullet); transaction-level `SERIALIZABLE` — turns concurrent allocators on different groups into false-positive serialization failures, broader than needed.

  Rust phase: identical pattern, `sqlx::query!` for the INSERT, manual `BEGIN`/`SAVEPOINT`/`ROLLBACK TO SAVEPOINT` via `sqlx::Transaction::execute`. `[settled]`
- **HTTP error response contract — RFC 9457 Problem Details**: every 4xx and 5xx response carries a body conforming to RFC 9457 (`application/problem+json` Content-Type), with shape:
  ```
  { type, title, status, detail, requestId, errors? }
  ```
  - `type`: defaults to `"about:blank"` until error-type URIs are published at a stable location (`https://ename.org/errors/<slug>`).
  - `title`: short human phrase, stable across instances of the same error (e.g. `"Validation failed"`, `"Idempotency conflict"`).
  - `status`: the HTTP status code duplicated in the body — useful for clients that log the body without the status.
  - `detail`: per-instance human-readable description, client-facing (no internal vocabulary).
  - `requestId`: custom extension member, the server-generated UUIDv7 echoed in the `X-Request-Id` response header — gives the client a value to quote when reporting an issue, greppable in server logs.
  - `errors` (optional): structured array `[{ path, message }]` populated for validation failures, where `path` is the JSON pointer into the request body (e.g. `["ename", "namePart"]`) of the offending field. Lets clients attach error messages to the right form input without parsing `detail`.

  Centralized in `src/api/problem.ts`: `ProblemDetailsSchema` (registered as `.openapi('ProblemDetails')` and referenced by every 4xx/5xx response in every route), `problemResponse(description)` helper for OpenAPI route definitions, `PROBLEM_CONTENT_TYPE` constant. Wired into the v1 sub-app via `OpenAPIHono({ defaultHook })` for Zod validation failures and `app.onError` for handler-thrown errors (domain or unexpected). Rust phase: equivalent struct deriving `serde::Serialize` + `utoipa::ToSchema`, returned by the `IntoResponse` impl on the app's error enum. `[settled]`
- **API contract — subject registration and ename addition endpoints (v1)**:
  - `POST /api/v1/subjects` registers a new subject together with its first ename atomically. Body: `{ idempotencyKey, subject: { kind }, ename: { namePart } }`. Produces one `subject.registered` event.
  - `POST /api/v1/subjects/{subjectId}/enames` adds an ename to an existing subject. Body: `{ idempotencyKey, ename: { namePart } }`. Produces one `subject.ename_added` event.

  Two endpoints rather than one polymorphic endpoint: each URL carries a single well-defined semantic, no `oneOf` body schema. The URL hierarchy (`/subjects` root, `/subjects/{id}/enames` nested) reflects the structural hierarchy of the registry — the subject is the entity that persists, the ename is a versioned attribute of it. The "no orphan subject" property is guaranteed by the body requiring `ename.namePart` on the registration endpoint, not by hiding the `/subjects` URL. Both request and response bodies are **nested by entity block** (`subject`, `ename`), mirroring the event payload shape — one mental model end to end, no flat-vs-nested impedance between layers. `[settled]`

## Open topics

- **[Q-PORT-TRIGGER]** Explicit trigger of the Node → Rust port. The default risk of the "Node now, Rust in 2-3 years" plan is that the moment of the port may never be self-triggered: the Node team grows, the system works, there is always something more urgent than rewriting a system that works. Three options: (a) calendar trigger (date set in advance, for example "port launched at most 24 months after the v1 production release"); (b) event trigger (arrival of the 2nd operator, security audit, traffic threshold crossed); (c) combination "first of the two". To be arbitrated before the v1 release and formally inscribed somewhere — otherwise the trigger does not exist in practice.
- **[Q-ID-PUBLIC]** Public exposure of internal technical identifiers. A subject being able to have multiple enames (name change case, and later aliases), the `subjects` table requires an internal identifier distinct from the enames. Three options: (a) `subject_id` strictly internal, the API exposing relations between enames (`/enames/<ename>/aliases`) rather than a subject id; (b) canonical ename designated as the public anchor of the subject, with no new exposed identifier; (c) `subject_id` itself exposed publicly alongside the enames. Tension with the principle of human-readable identifier: exposing an opaque technical id introduces a second public surface of designation, to carry over the multi-century lifespan of the registry. To be arbitrated before the stabilization of the OpenAPI contract.
- **[Q-LOG-STRUCT]** Exact cryptographic structure of the public event log. Choice between a linear log of the *Certificate Transparency* / Sigsum type (Trillian, Tessera), a sparse Merkle tree of the CONIKS / Google Key Transparency type, or a hybrid structure. Precise scheme of signed tree heads, frequency of publication, snapshot or epoch mechanism allowing a new verifier to bootstrap without replaying the entire history, possible external anchoring strategy (periodic publication of signed tree heads on a public chain for timestamping independent of the registry operator). To be settled during the Node phase, by prototyping. Conditions the public format of the log, its API surface and its compatibility with existing tools of the transparency log ecosystem.
- **[Q-CRYPTO-AGILITY]** Crypto-agility plan of the log on a multi-century horizon. SHA-256 and Ed25519 will not hold over the registry's durability horizon. The format must provide from v1: explicit versioning of the cryptographic suite within events and signed tree heads, mechanism for re-anchoring the entire log under a new hash function and/or a new signature scheme when evolution requires it, preservation of commitment chains between the old and the new root so that historical verifiability survives. To be treated jointly with [Q-LOG-STRUCT] and with [Q-CRYPTO-IMPL] *(defined in `ename-synthesis.md`)*.
- **[Q-OPKEY-MGMT]** Management of the registry operator's signing key (the one that signs log heads and operator events). Storage (dedicated HSM, cloud service such as Scaleway KMS, other), possible multi-signature scheme (signature required by k members of the board or by k partner operators for sensitive operations), rotation procedure, succession plan in case of loss or jurisdictional transfer. Near-irreversible decision once the first signed tree head is published — to be settled before the v1 production release.
- **[Q-REVOC-REASONS]** Codified reasons for revocations in the log. A revocation can be declared for compromise, retirement, death, or remain opaque. The distinction conditions what an external verifier can conclude about the value of a signed message *before* the revocation: a message signed before a compromise revocation does not have the same value as one signed before a retirement revocation. To be articulated with [Q-REVOC] *(defined in `ename-synthesis.md`, which deals with the policy of retroactive invalidation in case of compromise)*.
- **[Q-RECOVERY-PROC]** Procedure framing operator-mediated key recovery, as seen from the registry. Public effectiveness delays (for example, recovery announced at D, effective at D+N unless formal opposition), minimum identity re-verification requirements on the operator side, conditions and channel of public contestation, audit of the use of this procedure by accredited operators. Distinct from [Q-KEYREC] *(defined in `ename-synthesis.md`)* which deals with mechanisms on the user side; here, we deal with the institutional framing of operator use. Belongs mostly to the Ename regulation but has technical implications (encoding of delays in the log, scheme of contestation events).
- **[Q-LEGAL-DEMANDS]** Prepared position of the registry vis-à-vis legal demands for erasure, rectification or retroactive modification of data. The log being public and append-only, some requests are structurally impossible to honor; others (forced deactivation marking, for example) remain possible. Articulation to be prepared with legal counsel before the v1 production release. Concerns primarily the Ename regulation, but has implications for the operational response strategy and for the public documentation of the model.

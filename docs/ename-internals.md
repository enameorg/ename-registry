# Ename — Registry Internals

## Preamble

This document is the source of truth for the **internal architecture, conventions and code guidelines** of the Ename registry. It sits one level above the code: the code is the spec and its implementation; this document captures what the code cannot state about itself — cross-cutting invariants, conventions that constrain future code, and committed-but-unbuilt design. The trade-off behind a decision — its context, the alternatives rejected, its consequences — lives in an architecture decision record under `docs/adr/` ([ADR-0001](./adr/0001-record-architecture-decisions.md)), linked from the rule it explains; this document keeps at most a clause of justification where a rule is counter-intuitive. It does not repeat what a reader can infer from the code or an ADR, and it carries no setup or command reference (those live in each package's `README.md`).

Primary reader: the AI assistant that maintains the codebase. Secondary: the human team. Updates are delegated to the AI and land in the same change as the code decision they record (cf. `AGENTS.md`).

Scope: internal implementation decisions, **unilaterally revisable** by the registry's technical team. Out of scope: the public technical standards the registry publishes (ename format, signature of events, inter-platform transfers — see [Ename — Format](./ename-format.md) and [Ename — Signature](./ename-signature.md), modifiable only through public consultation per `ename-synthesis.md`), and the mission, governance and institutional model (`ename-synthesis.md`).

Status markers: unmarked text is **implemented and current**; `(working hypothesis)` is current and relied on by the code but may be revised; `(target)` is decided and shapes current code but is not yet built. Unresolved questions live in § Open questions under stable `[Q-XXX]` ids shared across the corpus, each referenced from the body of this document.

## Architecture overview

The registry is an **append-only event log**, the single source of truth for every registry mutation. The SQL database is a reconstructible projection of the log, serving fast reads. The log is public and auditable: this is what lets a commons survive centuries without resting on institutional trust alone.

The backend has two implementation phases: **Node.js + TypeScript** now, **Rust + axum + sqlx** later, ported by a dedicated team rather than migrated gradually ([ADR-0002](./adr/0002-node-first-then-rust-port.md)); the port's trigger is open (`[Q-PORT-TRIGGER]`). The versioned OpenAPI contract is the language-independent pivot the two phases share. Node code is shaped to map cleanly onto the Rust target; concretely this fixes a few choices repo-wide: raw parameterized SQL (no ORM), pure `function`s and module singletons (no DI framework, no classes with hidden state), snake_case in SQL, and the two-layer split below.

Code organization favors **global symmetry across the codebase** over per-module optimization. No size threshold triggers an isolated restructuring; a structural change lands everywhere at once. Current layout: one folder per concept within each layer.

## Event log and data model

**Event sourcing.** Every mutation (today: the registry's anchor, platform accreditation, platform key addition, subject registration and ename addition; later: key rotation, revocation, recovery, deactivation) is recorded as an immutable event. No retroactive modification or deletion. The SQL database can be fully rebuilt from the log ([ADR-0003](./adr/0003-event-log-as-source-of-truth.md)): each event kind writes its rows a second way, from what the event records — ids, counters and timestamp included, nothing allocated — and `rebuildEvent`, in the `event` concept, is the single path that writes one stored event's rows again. `rebuildProjections`, in the `application` concept, walks the whole log in `sequence` order and rebuilds each event through the definition of its kind. It writes only what the log records, into projections its caller has emptied: no production code empties a projection, and its only caller is a test. Each kind's test and the walk's test prove it (see Tests).

**Registry scope** `(working hypothesis)`. The registry stores only what binding and verification require — the ename, its subject and the subject's home platform, the accredited platforms and the legal entity holding each, and the public keys that sign events today; the subject's public key, key-transition history and lifecycle status are `(target)`. Profile data (display name, contacts, anything richer) is the platforms' responsibility, never the registry's. This keeps the auditable surface minimal and erasure structurally bounded; the registry's stance on legal demands for erasure or rectification is `[Q-LEGAL-DEMANDS]`.

**The `events` table.** The v1 embodiment of the event log — an append-only table from which every projection (`platforms`, `keys`, `subjects`, `enames`) is derived. Column types and the per-kind JSON shapes live in the migration and the service code; the invariants are:

- `sequence` (PK, `BIGINT` IDENTITY) — position in the log. Strictly monotonic but not gap-free (an aborted transaction burns a value, e.g. the idempotency race path). It guarantees only a total order over committed events, so it is _not_ a Merkle leaf index: the contiguous leaf index is assigned at tree-construction time `(target)`.
- `idempotency_key` (UUIDv7, UNIQUE) — client-provided, transport metadata. Distinct from the server-generated `requestId` (observability, never persisted).
- `kind` (CHECK-enumerated) — convention `<entity>.<verb-past-tense>`, a vocabulary value (see Vocabulary values) whose entity is the namespace and whose verb is in the past tense, because an event records a fact. `registry.anchored`, `platform.accredited`, `platform.key-added`, `subject.registered` and `subject.ename-added` are emitted today. Each kind is declared once, as an _event kind definition_ — the kind literal, the operation its signer requests (see Signed events), the pair of strict Zod schemas that parse its `request` and `outcome`, the pair of pure functions that map between the rows the use case writes and the event (`toOutcome` keeps of the rows what the server allocated, `fromEvent` reads a whole event back into the rows), and `rebuild`, which writes those rows again as the event records them — in the file of the use case that emits it; the `event` concept owns the shape of a definition, the write protocol and the rebuild of one event, and imports no other concept. The CHECK is the authoritative list of kinds, and a test pins that the definitions in code agree with it.
- `request` / `outcome` (two JSONB columns) — `request` is what the signer submitted, nested by entity; `outcome` is what the server allocated (UUIDv7s, sequenced counters). The split keeps apart the two scopes the signatures cover — `request` by the signer's signature, `outcome` by the layer-2 signed tree head `(target)` ([ADR-0004](./adr/0004-split-event-request-and-outcome.md)). Both exclude `idempotency_key` and `created_at`, which have their own columns.
- `signature_key_id` (UUIDv7) and `signature_value` — the signature as the signer submitted it, read back as one `signature` object: the key that signed the event's document and the value, from which anyone holding the log verifies the event again. `signature_key_id` has no foreign key: the log references no projection, since a rebuild empties them beneath it ([ADR-0012](./adr/0012-accreditation-and-keys-in-the-log.md)).
- `created_at` (TIMESTAMPTZ) — the single timestamp of the event; projection rows inherit it, at the first write as at a rebuild.

**Schema discipline (projections).** Consequences of "the log is the source of truth":

- `created_at` is supplied by the application, never `DEFAULT now()` — a default would make a rebuild non-deterministic. `withEvent` captures `createdAt` once per event and hands it to the use case's work, which propagates the same value to every INSERT, so all rows of an event share a byte-identical timestamp.
- No `DEFAULT` on `id` — UUIDv7 is application-generated; a missing id must fail loudly.
- Projections hold current state. A change to a projection row is an `UPDATE` made by the event that records it, and made again by that event, in log order, at a rebuild; the history of every change lives in the event log, never duplicated in a projection. A table whose rows may change carries `updated_at`, set, like `created_at`, from the event's timestamp — equal to `created_at` until the first change; a table whose rows never change, like `enames`, has none. Whether a row may change is its concept's business rule — an ename never changes once allocated. The log itself is append-only: no `UPDATE` or `DELETE` on `events`.
- Validation boundary: invariants that may evolve with the public format live in Zod; PostgreSQL `CHECK` encodes only invariants that survive every anticipable format change (length, absolute bounds, the broadest character class). This keeps a minor format change from forcing a DDL migration.
- Ensure every foreign-key column is indexed by effective coverage, not mechanically. A composite PRIMARY KEY, UNIQUE constraint or index whose leftmost column is the foreign key satisfies this; do not keep a narrower duplicate index unless a measured query plan needs it.
- `CHECK` constraints are named explicitly (auto-names are illegible in logs); PK/FK/UNIQUE keep PostgreSQL's predictable auto-names, unless the auto-name would pass the 63-character identifier limit and be truncated (`platforms_registration_key`).

**Primary keys.** UUIDv7 (RFC 9562), application-generated, stored in the native 16-byte `uuid` type, for every entity table; log tables use `BIGINT` IDENTITY (a log entry is a position, not an entity) ([ADR-0008](./adr/0008-application-generated-uuidv7-keys.md)). `subject_id` is exposed publicly as a reference that is stable across platforms and survives renames, and is validated by a strict lowercase pattern at every boundary (defined in `src/utilities/uuid.ts`).

**SQL naming.** snake_case for every identifier (tables, columns, indexes, constraints). Table names are plural, column names singular; a foreign key is `<singular_table>_id` referencing `<plural_table>.id` (e.g. `subject_id` → `subjects.id`). Avoid SQL reserved words even where PostgreSQL accepts them (`account` not `user`, `kind` not `type`).

**Vocabulary values.** A string that names a category on the wire or in the log — an event kind, an error-type slug `(target)`, a multi-word enumeration value — is lowercase kebab-case, with `.` as the namespace separator (`subject.ename-added`). The casing marks the category: a vocabulary value is neither a camelCase identifier (code, JSON keys) nor a snake_case identifier (SQL), so `subject.ename-added` cannot be read as a qualified `table.column` reference where a kind sits beside real identifiers, in the `CHECK` of the migration. A column holding a vocabulary value (`events.kind`, `subjects.kind`) is `CHECK`-enumerated and the vocabulary grows by migration: a vocabulary is a closed list, not a format, so the validation-boundary rule that keeps a `CHECK` broad does not apply to it.

**Idempotency.** Every write endpoint takes a mandatory `idempotencyKey` (UUIDv7) in the body, not a header, so that the event's signature covers it ([ADR-0005](./adr/0005-idempotency-key-in-body.md)). One function, `withEvent` in the `event` concept, runs the protocol for every write use case: the request parsed with the kind's strict schema and checked for values every implementation reads alike — no string that is not well-formed Unicode, which JCS cannot canonicalize, and no number JCS writes with a fraction or an exponent — and the idempotency key and the signature parsed, a failure of any of them raised as a `ValidationError`; the signer authenticated on the signable document the protocol builds, by the function its use case passes (see Signed events), before anything is looked up, so an unauthenticated request gets neither a write nor a replay; a preliminary lookup outside the transaction; the use case's work, run inside the event's transaction with the event's single `createdAt`, its result reduced by the kind's `toOutcome` and parsed with the kind's strict schema; a final `INSERT events` whose UNIQUE violation signals a concurrent winner to reconcile against; reconciliation that compares, in order, the signing key — two keys of one owner are two signers, so a retry is signed by the key that signed the first request, and the signature's bytes are never compared, since ECDSA signs the same document differently each time — the kind, and the request, by structural deep-equality with the stored `request`. A first write returns the work's result; a replay returns what the kind's `fromEvent` reads from the stored event, the same thing by the law each kind's test pins (`fromEvent` of `toOutcome` of the rows is the rows); the same key from another signer, or with a different request (body or path), returns 409. Any domain error raised by the work is confronted with an idempotency winner before it surfaces: a request that lost the race to an idempotency winner may hit a current-state conflict the winner explains, and the replay wins. Uniqueness is global; the isolation between signers is the reconciliation's comparison of signing keys: a signer never reads another's result by reusing its idempotency key.

**Group-scoped counters.** A counter unique within a group (today `enames.number_part` per `name_part`) is allocated inside the INSERT via `COALESCE(MAX(...), 0) + 1`, guarded by a `UNIQUE (group, counter)` and retried on collision, each attempt in a nested `withTransaction`. The retry budget bounds the concurrent burst a single group can absorb; exhaustion raises a retryable `ContentionError` (→ 503), never an opaque 500. Both are a safety net, not a hot path: with civil names, two allocations of the same `name_part` within one transaction window stay rare even at a billion users ([ADR-0007](./adr/0007-concurrency-by-constraints-and-retry.md)). No further mechanism is planned for a hot group; advisory locks are unavailable (see Serverless SQL constraints).

**Subject-scoped name uniqueness.** A subject can hold several enames, but only one per `name_part`. The database enforces this with `UNIQUE (subject_id, name_part)`. The public `number_part` is allocated globally per `name_part`, so the same `name_part` can belong to different subjects as different full enames.

**Signed events.** Every event is signed over the document [Ename — Signature](./ename-signature.md) defines — the kind's operation, the signing key's id, the idempotency key and the request — and the log stores the key's id and the signature, from which anyone holding the log verifies the event again ([ADR-0011](./adr/0011-authenticate-by-signing-the-event.md)). The write protocol builds that document and hands it to the authentication its use case passes, which returns the signer or refuses it: the protocol itself knows no key. One `key` concept holds the public keys of every signer, a key with no platform being a registry key, and establishes that a recorded key signed a document: a signature that does not verify, or names an unknown key, is one `AuthenticationError`, so a caller never learns which keys exist. Which keys an operation admits is the business of the concept that owns them — `authenticatePlatform` in `platform`, `authenticateRegistry` in `registry` — and a verified key of another owner is an `AuthorizationError`; so is a platform adding an ename to a subject it is not the home platform of, a check the use case's work makes against the current state. The home platform of a subject is the platform whose key signed its registration, recorded in the event's outcome. The registry submits its own events — accrediting a platform, adding a platform key — through the same signed API, signed by a registry key held outside the server, which only verifies ([ADR-0012](./adr/0012-accreditation-and-keys-in-the-log.md)). The first event of the log, the anchor (`registry.anchored`), adds the first registry key and is signed by that key, under the id its holder chose: its use case authenticates it against the key it adds, and the initialization command, which reaches the database directly, writes it through the write protocol like any other event. A unique index admits one anchor in the log, and the anchor comes first, since every other event is signed by a key an earlier event recorded. Adding a registry key after the anchor waits on `[Q-REGKEY-MGMT]`; both it and the revocation of a platform key are conditions of going into production `(target)`. A rebuild does not verify signatures: each kind's test verifies those of the events its use case stores, and a verification of the whole log, the check a third party runs, is `(target)`.

**Cryptographic model** `(target)`. The log-level cryptographic layer is not built yet; it shapes the current schema (the `request`/`outcome` split, the in-body idempotency key), and the commitments it will publish bind the registry long-term — so the scheme must be conservative, portable and crypto-agile (cf. `[Q-LOG-STRUCT]`, `[Q-CRYPTO-AGILITY]`, and `[Q-CRYPTO-IMPL]` in `ename-synthesis.md`).

- _Verifiability._ Events are chained in a Merkle structure; the registry periodically publishes signed tree heads so any third party can verify that an event is in the log and that history has not been rewritten. The whole log is public and downloadable. Custody, rotation and succession of the registry key, which signs the tree heads, are `[Q-REGKEY-MGMT]`.
- _Signature taxonomy._ Any event that transfers or modifies **control** of an ename is cryptographically chained to the previous user key, or explicitly labeled a recovery; any other event is signed by the platform key of the platform that submits it, except the registry's own events — accreditations, keys, log mechanics — signed by a registry key. Whether a revocation carries a codified reason or stays opaque is `[Q-REVOC-REASONS]`.

  | Event                                                | Signed by                                                                         |
  | ---------------------------------------------------- | --------------------------------------------------------------------------------- |
  | Initial registration, ename addition                 | Platform alone (no prior user key; mis-registration stays detectable by the user) |
  | Key rotation, user-declared revocation, deactivation | Current user key                                                                  |
  | Key recovery                                         | Platform alone, explicitly labeled and publicly visible                           |
  | Platform accreditation, platform key addition        | Registry alone                                                                    |
  | Log mechanics (registry key rotation, checkpoints)   | Registry alone                                                                    |

- _Recovery._ A key transition not chained to a valid user key is encoded as a labeled, publicly visible recovery event. How the user proved their recovery right is platform-side and external to the registry (`[Q-KEYREC]` in `ename-synthesis.md`). The registry refuses the pure-lockout model (lost key = lost ename), which is untenable at the scale of a universal human identity. The institutional framing of recovery as the registry sees it — delays, re-verification, contestation, audit — is `[Q-RECOVERY-PROC]`.
- _Initial registration._ The platform submits the user's public key with no proof-of-possession required by the registry; a mis-registered key is a visible attack (the user cannot sign under their ename), not a silent one. Proof-of-possession may be added later.
- _Transition monitoring._ A home platform must watch the log for the enames it serves and alert users on any unsolicited transition; without it the chaining protects only retroactively (cf. `[Q-ACCRED-CRITERES]` in `ename-synthesis.md`).

## Application architecture

**Two layers, no Repository.** The **API layer** (`src/api/`) is the HTTP surface — routing, input/output validation, serialization, status codes — and holds no business logic. The **Service layer** (`src/services/`) holds all business logic and accesses the database directly ([ADR-0006](./adr/0006-two-layers-without-repository.md)). Low-level DB plumbing (the pool, the query and transaction helpers) lives in `src/database/` and is consumed only by the Service layer. The Service layer holds six kinds of function, kept distinct: **data-access primitives** (single-table reads and writes in raw parameterized SQL, mapped through Zod), **pure business-rule functions** (testable without a database), **signer authentications** (`authenticateKey`, in `key`, reads a key and verifies a signature; each concept that owns keys narrows it to the keys it admits — `authenticatePlatform`, `authenticateRegistry` — and the anchor's verifies against the key its own request adds), **use cases** (one operation each: the work that writes the operation's rows and returns them, in the concepts' own types, and the definition of the event kind it emits, whose three functions map those rows to the event, read them back from it, and write them again at a rebuild; the use case returns what its work returns, so it reads top-down, at the price of the law the kind's test pins), the **protocols** the `event` concept owns — the write protocol (`withEvent`), which authenticates the signer through the function the use case passes, runs every use case's work inside the event's transaction with the signer it returns, owns idempotency, and returns the work's result, or on a replay what the kind's `fromEvent` reads from the stored event; and the rebuild of one event (`rebuildEvent`), which writes a stored event's rows again through the kind's `fromEvent` and `rebuild`, allocating nothing and appending nothing to the log — and the **application operations**, which the `application` concept holds above every aggregate: what spans them all (`rebuildProjections`, which rebuilds every event of the log through the second protocol) and what the running process needs (the health probes, the release of the database at shutdown). A use case never opens the transaction or touches the log itself — the `event` barrel does not export the log's write primitive, so nothing outside the concept can.

**Data-access primitives and information hiding.** Each concept's primitives are the sole holder of its schema knowledge — table and column names, SQL text, constraint names, expected PostgreSQL error codes — and they translate expected DB errors into domain errors, so nothing above them branches on a SQLSTATE or a constraint name. This is _information hiding_, not an abstraction layer: no indirection, no substitutability, the SQL owned and visible, merely confined. Three concerns, three homes: schema → primitives; transactions → the write protocol (at a rebuild, its caller); generic pg mechanics, the recognition of an unavailable database included → `src/database/`. Every primitive takes its connection first, `db: Database` — the union of the pool and a transaction's client, exported by the query helpers — so the same read serves a lookup outside any transaction and a check inside one, and a write called with the pool runs in a transaction of its own. `Pool` and `PoolClient` appear only in `src/database/`; everything else takes `db: Database`. A use case does not pre-check an invariant already enforced by the database when the write primitive can translate the expected constraint violation into a domain error. For write paths, prefer the write plus constraint translation over read-before-write; a pre-check is justified only when it enforces a rule the database cannot express, avoids expensive work before a known failure, or improves semantics without replacing the database constraint. The same holds after the write: an invariant only the written row can state — the 52-character budget of an ename, known once its `number_part` is allocated — is a `CHECK` the allocation translates into a `ValidationError` like any other constraint. What a write primitive promises is a valid row, or a domain error for every failure a caller can cause: it returns the row as the database wrote it (`RETURNING`, parsed by the row schema), so no caller reassembles it from the parameters, and no caller runs a rule after it. A failure no caller can cause is not translated: the verbatim insert a rebuild uses lets a violated constraint surface raw, since it means a corrupted log or projections that were not empty.

**Concept folders and naming.** Each layer holds one folder per concept, exposing its public surface through an `index.ts` barrel — the encapsulation boundary. Intra-folder code imports files directly; other folders import through the barrel. Within a Service concept, the concept-named file (`subject.ts`) carries the domain type/schema, the primitives, and its pure rules; each use case is its own operation-named file (`register-subject.ts`). The `event` concept additionally carries the shape of an event kind definition (`event-kind.ts`), the write protocol (`with-event.ts`) and the rebuild of one event (`rebuild-event.ts`); a kind is declared in the file of the use case that emits it, below the use case, so the file reads top-down as what the operation does, then what the log records of it, how it reads back and how it is rebuilt, and `event` sits below every other concept without importing one — the cycle a kind composed from an aggregate's input schemas would otherwise close through that aggregate's barrel — and authenticates no signer itself. `key` sits below the concepts that own keys and imports no other concept; the authentication of a signer and the use cases that add keys live with the owner (`platform`, and `registry`, which holds what the registry records of itself). The Service layer's root holds what spans its concepts: its errors, its context, and its test helper. Beside the concept folders, `services/common/` holds the sub-concepts several concepts share, with no table and no use case of their own — today the signature of a request, which the signers create, their authentication verifies and `event` checks again on a stored event: it imports no concept, any concept imports it through its barrel, and it differs from `src/utilities/` by carrying a rule of the Ename domain, what a request signs. The `application` concept imports the aggregates' barrels: `rebuild-projections.ts` holds the walk over the whole log and, beside it, the list of every event kind definition, where a new kind is added. In the API, a URL-root folder holds one file per route plus one concept-named file per concept it owns, one whose every instance belongs under that root (`api/subject/subject.ts`, `api/subject/ename.ts`: the OpenAPI components a client sees); its barrel exposes the routes, their handlers and those schemas, and `api/index.ts` registers the routes through it. The wire schemas of a concept no URL root owns live in `api/common/`, a folder that mounts no route and exposes its schemas through a barrel like the others: `Signature`, which every write body carries, and `Key`, which a platform or the registry holds. A concept that gains a URL root of its own moves to that root's folder. Outside the two layers, `src/utilities/` holds the pure modules both layers import directly — no I/O, no singleton, no knowledge of a layer — one file per concept it owns (`uuid.ts`, `date-time.ts`, `signature.ts`), its test alongside, and under `test-data/` the third-party vectors a test reads, copied verbatim with a `NOTICE` naming their source. The folder is not a concept, so it has no barrel: a consumer imports the file, and a utility that outgrows one file becomes a concept folder with its own barrel. Grouping mirrors across layers — the API by URL root, the Service by aggregate: a nested write such as `POST /subjects/:id/enames` becomes an API file under `subject/` and a use case under `subject/`. Concept folders are singular at every layer (`subject`, `ename`), so a concept carries one name across the whole codebase — chosen for cross-layer symmetry over echoing the plural REST URLs and SQL tables (the route path stays explicit in each `createRoute`).

**Per-layer visibility.** A resource appears only at the layer that consumes it: the pool, the SQL helpers and transactions stay in the Service layer; the API layer's `APIContext` (Hono's request context) carries only what it needs at request time.

**Dependency propagation.**

- Stateless functions: direct import, `(input) → output`.
- Process-lifetime resources (config, root logger, pool): module singletons, frozen after init, imported by their consumers; the pool lives in a Service-layer module and is invisible to the API layer.
- Request-scoped values (requestId, child logger): carried on the API layer's `APIContext` via `context.var.*`, populated by middleware.

A request-scoped value the Service layer needs is read from the `APIContext` by the handler and passed as an explicit argument (`ServiceContext`); the Service layer never touches the `APIContext`. A `PoolClient` opened for a transaction flows the same way — an explicit argument between service functions, never an ambient value ([ADR-0010](./adr/0010-thread-the-database-connection-explicitly.md)), never up to the `APIContext`: the write protocol opens it through `withTransaction(pool, work, logger)` and hands it to the use case's work as its `db`, which passes it on to each primitive; a read outside a transaction passes the pool singleton. The transaction helper takes both the connection and the logger as arguments: the query helpers import no singleton, and the rollback-failure log keeps the request's `requestId`.

**Domain errors and HTTP mapping.** The Service layer throws semantic errors (`DomainError` and its subclasses `ValidationError`, `AuthenticationError`, `AuthorizationError`, `NotFoundError`, `ConflictError`, `IdempotencyConflictError`, `ContentionError`) and knows nothing about HTTP. Beside them, `UnavailableError` says the database did not answer: `src/database/` raises it for every statement its helpers run, and the Service re-exports it under that name, so the API maps it without knowing the database. It is not a domain error, so the write protocol never confronts it with an idempotency winner; a client retrying under the same key gets the replay. It lets no library error out for a fault of the caller: a Service function that rejects a client's input raises a `ValidationError`, never a `ZodError`, and a request that fails its kind's strict parse in the write protocol becomes one through the Service's single translation of a Zod failure (`validationErrorFromZodError`, in `src/services/errors.ts`), so the `ValidationError` → 422 branch below covers every caller, HTTP or not. A parse that fails on what the server produced — an outcome, a stored event read back on a replay — is a bug or a corrupted event, not a malformed request, and surfaces through the 500 fallback. The API's error module (`src/api/errors.ts`) owns every answer to an error, so the version's assembly module stays a bare mount table: the Problem Details shape, the validation hook (422, built through the same translation, so it answers exactly what the mapping answers for a `ValidationError`), the 404 catch-all and the 405 responder, the gate responses a route with a JSON body spreads into its OpenAPI `responses` (400, 413, 415; the 422 stays the route's, its description naming what the route validates) the signature responses a signed route spreads beside them (401, 403), the conflict response every write route spreads (409) and the unavailable response every write route spreads (503, for a database that does not answer or a counter under contention), each with one description shared by every route, and the single error mapping: `ValidationError` → 422, `AuthenticationError` → 401 + `WWW-Authenticate: EnameSignature` (RFC 9110 requires a scheme on every 401; the signature travels in the body, not in an HTTP authentication scheme proper), `AuthorizationError` → 403, `NotFoundError` → 404, `ConflictError` and `IdempotencyConflictError` → 409, `ContentionError` and `UnavailableError` → 503 + `Retry-After`, the second logged at error level since an outage must alert, a framework-raised Hono `HTTPException` (a malformed JSON body, reported as 400; a request body over the size cap, reported as 413; a request body whose media type is not the declared `application/json`, reported as 415) → its carried status with our own client-facing text, any other `HTTPException` → its status with a generic text, anything else → 500; both fallbacks log the error. A problem's `title` derives from its status; the mapping overrides it only to name a sub-type a client must tell apart (`Idempotency conflict` on the idempotency 409), a distinction error-type URIs take over `(target)`. Error messages are written for the client (generic, no internal vocabulary); the specifics go to the logs, correlatable by `requestId`. A shared lower-level function emits operation-neutral client messages: if the same primitive serves registration, ename addition, imports or future tools, its errors name the shared operation (`ename creation`, `request`) rather than one caller (`registration`, `body`).

**Transactions.** The event's transaction is opened explicitly by the write protocol (`withEvent`, via the `withTransaction` helper) and the use case's work runs inside it; a use case never opens a transaction itself, and there is no transparent transactional middleware. The rebuild of one event opens none either: its caller passes a transaction's client, so that an event writing several rows is rebuilt atomically. The helper nests by the type of the connection it is given: a transaction on the pool, a savepoint on a client — a `withTransaction` inside a `withTransaction` is a savepoint, and the helper is the only module that knows the words `BEGIN`, `COMMIT` and `SAVEPOINT` ([ADR-0010](./adr/0010-thread-the-database-connection-explicitly.md)). A nested block that fails is rolled back to its savepoint and rethrows its own error; the enclosing transaction stays usable and its caller decides — retry (the counter allocation runs each attempt in a nested block) or let it propagate. Two constraints follow: no parallel statements inside one transaction (two nested blocks on the same client interleave their savepoints, and releasing the first drops the second), and a loop releases at each turn, because PostgreSQL degrades past 64 open subtransactions in one transaction.

**Concurrency.** Concurrent writes are made safe by UNIQUE constraints plus bounded optimistic retry — the idempotency key and the group-scoped counter both race, hit the constraint, then reconcile or retry; a second anchor is refused by a unique constraint as well: the index that admits one anchor, or the primary key of `keys` when it reuses the recorded `keyId`. The registry relies on neither SERIALIZABLE isolation nor advisory locks ([ADR-0007](./adr/0007-concurrency-by-constraints-and-retry.md)); a new concurrent-write path follows the same constraint-plus-retry shape.

**Error cleanup.** A cleanup action in a `catch` — `ROLLBACK`, `ROLLBACK TO SAVEPOINT`, a release — must never mask the original error: wrap it so the original propagates, and log the cleanup failure separately. Applies to all current and future manual-transaction or SAVEPOINT code.

**Assembly vs runtime.** The module that assembles the app (`src/index.ts`) has no side effects and is importable by tests that drive it via `app.fetch(request)` without opening a port. The module that runs it (`src/server.ts`) adds the listener, signal handling and graceful shutdown; shutdown releases the database through the Service layer's `closeDatabase`, never through `src/database/` directly.

## API and HTTP contract

**OpenAPI 3.1, code-first.** One document per API version, produced by the version's sub-app with paths relative to its mount and a `servers` entry carrying the prefix, in two representations from the same generator function: the canonical versioned file (`backend/openapi.json` for v1; committed, the audit trail, consumed off-runtime by SDK generators and CI) and the runtime spec at `/api/v{N}/openapi.json` (generated per request, always in sync with the running code). A contract test fails on any byte of drift between the two, so the committed file is regenerated in the same change as a route. The interactive reference at `/api/v1/docs` is an interim convenience: the page is a skeleton that loads the Scalar bundle from jsDelivr, a third-party script served under the registry's domain. The reference page moves to the frontend, pinned to a Scalar version and reading the runtime spec; the backend then serves only `openapi.json`, the `/docs` route and its Scalar dependency go away, and the backend accepts the frontend's origin (CORS) `(target)`.

**Versioning.** Each major version is a sub-app mounted under its prefix (`/api/v1`); routes are defined without the prefix (applied at mount). v1 and v2 cohabit as two mounts. Each version owns its fallbacks inside its sub-app, because `app.route()` copies a sub-app's routes but not its `notFound`: a terminal catch-all route answers an unmatched path with a Problem Details 404, and Hono's method-not-allowed middleware answers an unsupported method on a known path with a Problem Details 405 and an `Allow` header. The root app is a bare mount table; a path outside every version prefix gets Hono's default text 404, which is outside the contract.

**Endpoints.** Registration is `POST /api/v1/subjects` — it creates a subject and its first ename atomically and emits one `subject.registered` event (a subject without an ename has no meaning). Adding an ename to an existing subject is `POST /api/v1/subjects/:id/enames`, emitting `subject.ename-added`. The registry's own events have their endpoints: `POST /api/v1/platforms` (`platform.accredited`, a platform and its first key) and `POST /api/v1/platforms/:id/keys` (`platform.key-added`); the anchor has none. Every write body carries a `signature` object beside the request it signs. Every route carries an `operationId`, the name of its route in code less the `Route` suffix (`registerSubject`), after which an SDK names its method; a write route also names the operation it signs in an `x-ename-operation` extension, since the `operationId` belongs to one API version where the signed operation stays the same across versions. Single-purpose endpoints rather than one polymorphic body; request and response are nested by entity (`subject`, `ename`), mirroring the event `request`/`outcome` shape — one mental model from wire body to log entry. Each entity object is one OpenAPI component, shared by every route that carries the shape, so an SDK generator emits one type per concept: `Subject`, `Ename`, `Platform` and `Key` are the resource as the registry returns it, `SubjectReference` and `PlatformReference` id-only objects naming an existing one (what the event request carries), `SubjectInput`, `EnameInput`, `PlatformInput` and `KeyInput` the objects a client submits, `Signature` the signature every write body carries. Only the route envelopes (`RegisterSubjectRequest`, `AddEnameToSubjectResponse`, …) carry an operation's name; an entity object would too if its shape were specific to one operation. (The live endpoint list is in `backend/README.md`.)

**Problem Details (RFC 9457).** Every 4xx and 5xx response is `application/problem+json` with `{ type, title, status, detail, requestId, errors? }`. `type` is `about:blank` until error-type URIs are published at `https://ename.ngo/errors/<slug>` `(target)`. `requestId` is the server-generated UUIDv7 also returned in the `X-Request-Id` header; `errors` is the field-level array for validation failures. Text casing follows the field's grammatical role: `title` is a short capitalized label with no terminal period (`Bad request`); `detail` is a complete sentence, capitalized and period-terminated (`The request body is not valid JSON.`); each `errors[].message` is a field-attached fragment, lowercase and unpunctuated. Client-facing strings carry no framework-internal vocabulary — a framework message (e.g. Hono's malformed-JSON text) is replaced by our own before it reaches the client. A route's OpenAPI response `description` stays generic and stable per status code (`Request body failed validation`, not an enumeration of every cause); the cause specific to one occurrence lives in the response body (`detail`, and `type` once error-type URIs exist), not in the static contract text. This keeps the description from needing an edit each time a new cause maps to an existing status.

**Request body size.** Every request body under a version is capped at 64 KiB by a version-level middleware, registered before routing: it refuses on `Content-Length` alone when the client announces the size, and cuts the stream at the limit otherwise; the excess answers a Problem Details 413. The cap is an internal protection set far above any legitimate body (a registration is about 150 bytes), not a contract value: only the 413 response is contractual, and the value is revisable without a contract change.

**Serialization.** camelCase JSON keys. A timestamp is an RFC 3339 date-time in UTC, the form `toISOString()` emits (`DateTimeSchema`). A `BIGINT` field whose value is unbounded over the multi-century horizon (log positions, leaf indexes) is serialized as a `string` to preserve precision beyond 2^53 `(target)`; a bounded domain counter (`number_part`, at most 12 digits) stays a JSON `integer`.

## Code conventions

**Language and runtime.** TypeScript in strict mode plus the extra safety flags in `tsconfig.base.json` at the repository root, which every package's `tsconfig.json` extends. Node 26, ESM, run build-less via native type stripping (`node src/server.ts` — no `tsc` emit, no bundler, no loader); `tsc` is typecheck-only, and `erasableSyntaxOnly` forbids any TS construct that needs a runtime transform.

**Naming.** Explicit, fully-spelled names, no abbreviations (`context` not `c`, `error` not `err`, `request` not `req`), even where a framework's examples abbreviate. Exceptions: `id`, acronyms (`url`, `http`, `db`), the loop variable `i`, and a key a library acts on by name (pino's `err`). An acronym or initialism keeps a single case inside a name: all capitals after the first word (`readJSON`, `UUIDv7Schema`, `APIContext`), all lowercase when it opens a camelCase name (`db`, `url`, `jsonBody`). A proper name keeps its own spelling, its first letter lowercased only when it opens a camelCase name (`OpenAPI`: `renderOpenAPIDocument`, `openAPIMetadata`). `id` is an abbreviation, not an acronym: `requestId`. SQL, environment variables and file names keep their own case (`DATABASE_URL`, `openapi-metadata.ts`).

**Function form.** `function` declaration for top-level exported functions; the arrow form only for handlers and callbacks whose type lives on the binding via a framework helper.

**Avoid over-DRY.** Keep code direct when the shared part is only argument forwarding, a one-line expression, or a tiny branch that makes each caller less readable. Duplication is cheaper than indirection when two functions name distinct operations but happen to share mechanics. Extract only when the helper owns real shared behavior, such as parsing, transaction handling, retry logic, error translation, or a rule that must change in one place.

**File layout.** High-level functions come before the lower-level ones they call (stepdown order), so a reader meets a module's purpose before its mechanics; this works because `function` declarations hoist. Types follow the same order — they hoist too, so a type that is the private detail of one declaration sits just after it, the way a helper function sits after its caller. A load-time declaration — a constant, a Zod schema, (in the API layer) the route's `createRoute` definition — cannot follow a consumer that is itself evaluated at load time (a schema composing it), so those form a short dependency-ordered preamble above the functions; one read only inside a function body (an event kind definition handed to the write protocol) follows the function in stepdown order, the mechanics after the purpose. A type shared across the module (a `z.infer` twin of its schema, a shape several functions use) belongs in the preamble, not trailing one consumer.

**Comments.** A comment explains what the code cannot state itself: a non-obvious _why_, a trap, or an invariant spanning several lines. It does not restate the code, and it does not re-explain cross-cutting design this document owns or a trade-off an ADR owns — it points to `ename-internals.md` by name (never a section heading, which churns) or to the ADR by id (`ADR-0005`). Implementation-local rationale lives in the comment next to the code, not in this document or an ADR. Keep comments short and plain.

**Zod.** v4 at every boundary (HTTP input, HTTP output, DB rows). Schemas are declared at module top level — never rebuilt per request, since Zod's JIT cache keys on schema identity. They live with their consumer, and a shared schema is exported from the module that owns the concept. No `.openapi()` and no serialized format in the Service. A scalar rule (`NamePartSchema`, `SubjectKindSchema`, `UUIDv7Schema`, `DateTimeSchema`) and an input schema — the strict object a client submits for one entity (`SubjectInputSchema`, `SubjectReferenceSchema`, `EnameInputSchema`) — are declared once, in the module that owns them; the event kinds compose the input schemas into their `request`, and the API wraps both in place with their example (`UUIDv7Schema.openapi({ example })` at a field, `EnameInputSchema.openapi('EnameInput', { example })` for a component: a clone that leaves the original untouched) instead of re-assembling the shape, so the contract cannot drift from what the log stores and a client-facing message has one home. A wrapped schema keeps its name on both sides, so an API module that wraps a concept's schema imports that concept's barrel as a namespace (`subjectService.SubjectInputSchema`) rather than aliasing each homonym. The API owns outright the route envelopes, the path parameters and the response schemas, which carry serialized formats (a timestamp as a string) and merge request and outcome; a Service domain object (`Subject`, `Ename`, a row) never reaches the wire as is: the crossing is an explicit field-by-field mapping in the handler, not a chained `.transform()`, and a field a row carries but the wire does not (`subjectId`, a row's `createdAt`) stops there. A Service scalar that coerces a database representation (`NumberPartSchema`) is not wrapped: the wire field is its own and shares only the bound. HTTP input objects are strict (`z.strictObject`) at every nesting level: an unknown field is a 422 naming the key, never silently dropped, so the validated request is exactly what the client submitted — the property the signature over `request` relies on ([ADR-0011](./adr/0011-authenticate-by-signing-the-event.md), [ADR-0004](./adr/0004-split-event-request-and-outcome.md)). The `request` and `outcome` schemas of every event kind are strict too, at the seam that stores them: a field the wire accepts but the kind does not declare, or a field a kind's `toOutcome` keeps without declaring it, fails the write instead of being stripped on its way into the log.

**Configuration.** Each local environment is declared whole in its own file, per package: `.env.development` and `.env.test`, each copied from a versioned `.example`. A script loads its environment's file with `--env-file`, which fails when the file is missing; production loads none and gets its variables from the deployment. The code names no environment and reads a single `DATABASE_URL`, whatever database the loaded file, or a variable exported in the shell, points at. In the backend, the environment is read and validated once, in `src/config.ts` (Zod schema, fail-fast on invalid config); the rest of `src/` imports the typed `config` singleton and never reads `process.env` directly. A command under `scripts/` runs outside the server and may read a variable of its own.

**Logging.** `pino`, emitting JSON in every environment including local dev, so the production log format is familiar from day one. Logs may carry registry values (a `namePart`, a submitted request body): the registry's data is public by design, so a value in a log exposes nothing the database does not. The rule is revisited the day the registry holds a non-public value.

**Lint and format.** Prettier owns formatting, left at its defaults except `singleQuote` and `printWidth: 100`. ESLint complements it without overlap and runs no opaque preset — each rule is individually justified (type-aware promise hygiene, import ordering and hygiene, unused-import removal, comment width). Comment width is where one takes over from the other: Prettier wraps code at its width but leaves comments as written, so ESLint's `max-len` checks a line holding only a comment at the same 100, URLs aside, and leaves code to Prettier; a comment that follows code on its line is bounded by neither. The import boundaries this document states are ESLint rules too, so a violation is red before any review: the HTTP framework stays in the API layer; nothing below the API imports it; the API never imports `src/database/`, except `database/testing.ts` from a test; `pg` appears only in `src/database/`, and the Service layer calls no `.query` of its own; the `event` and `key` concepts import no other concept, only `services/common/`, which imports none; a utility knows no layer; another concept folder is imported through its barrel; under `src/`, `process.env` is read in `config.ts` only; a Node built-in carries the `node:` prefix.

## Tooling and supply chain

**Package manager.** npm 12+ with a versioned `.npmrc`: `min-release-age=3` (days), `strict-allow-scripts=true`, `engine-strict=true`. Dependency install scripts run only when the `allowScripts` field of the root `package.json` allows them; a dependency not covered fails the install, so every script is reviewed explicitly (`npm install-scripts approve|deny`, version-pinned by default) and the review is committed. `ignore-scripts` is never set: it overrides `allowScripts` and would silently disable the policy. `allow-git` and `allow-remote` keep npm's `none` default. `lockfile-lint` and a CI check that `.npmrc` still enforces the policy are `(target)` (no CI yet).

**Guardrails.** A versioned pre-commit hook, `.githooks/pre-commit`, runs the fast checks on the whole repository before every commit: typecheck, lint and format, in about seven seconds and without the database. The tests stay a deliberate `npm run check`: they need PostgreSQL, and a hook that fails because Docker is down is a hook that gets bypassed. The root `prepare` script activates the hook through `core.hooksPath` at every `npm install`, with no dependency and no install script to allow; `git commit --no-verify` skips it. Before each commit the agent also reviews the uncommitted diff with the project skill `review-diff` (`.claude/skills/`), whose text is the procedure: two sub-agents that did not write the code check it against this document and hunt the documents and comments it makes false. A CI running the full check on every push is `(target)`, the hard gate the hook only anticipates.

**Workspaces.** The repository is one npm workspace tree: the root `package.json` lists `database` then `backend` explicitly (`website/` holds no Node package), and one `package-lock.json` and one `node_modules` live at the root. The toolchain (`typescript`, `eslint` and its plugins, `prettier`) is declared once, in the root `devDependencies`, with one `.prettierrc`, one `eslint.config.js` (ESLint resolves it upward from each linted file) and a `tsconfig.base.json` every package extends; a package declares only what its own code imports. The `.npmrc` policy and the `allowScripts` allowlist live at the root, where `npm install` runs and where `npm install-scripts` writes; npm ignores a `.npmrc` inside a workspace. Dependencies are hoisted (npm's default); `import-x/no-extraneous-dependencies` guards against importing a dependency a package does not declare. No package depends on another: `database` is consumed through its commands, never imported. The root scripts fan out to the workspaces (`npm run test --workspaces`, in declared order), except `format`, which first checks the root's own files under a root `.prettierignore` that leaves each workspace to its own; a package-specific command runs from the root with `-w` (`npm run db:up -w database`), or from inside the package. A container image builds from the repository root (`npm ci -w backend --omit=dev`) `(target)`.

**Dependencies.** Prefer the platform (`node:` built-ins, native runtime features) over a third-party package; weigh a dependency's maintenance health and supply-chain surface before adding one.

**SQL access.** `pg` with parameterized raw SQL; rows are parsed through Zod at the boundary. Every statement goes through the query helpers — `queryRows` (parse plus snake_case-to-camelCase conversion), `withTransaction`, the health probe's `pingDatabase` — which turn a database that does not answer into an `UnavailableError`; a write returns what it wrote (`RETURNING`), so the Service layer never calls `db.query` itself. pg raises its connection failures without a code, so the helpers recognize them by message as well as by SQLSTATE and system error code, and a plumbing test produces each one for real. Cases outside these (`LISTEN`/`NOTIFY`, `COPY`, streamed cursors) get their own helpers when they appear.

**Database package.** Schema, migrations, the migration runner and the local PostgreSQL cluster live in the `database/` package, sibling to `backend/` and shared by every consumer of the registry's database — the Node backend today, the Rust backend later, future tooling. Migrations are pure SQL files named `<unix_ts>_<name>.sql` and forward-only: there are no down migrations, and a local rollback is a database reset ([ADR-0009](./adr/0009-forward-only-frozen-migrations.md)). The runner is a library, `database/src/migrate.ts`, exporting `run(client, migrationsDirectory)` over a connection the caller owns, with no side effect at import; `database/scripts/migrate.ts` is the thin CLI that connects to the database `DATABASE_URL` names, runs, and turns the result into an exit code. Before applying anything, the runner confronts the applied migrations with the files on disk: an applied migration is frozen in content and presence, so an edited, deleted or renamed file is reported and the run refuses. It then applies each pending migration, in lexicographic order and on that single connection, in its own transaction holding a transaction-level advisory lock under which the migration is re-checked as still pending (overlapping runners serialize and converge; the primary key on `schema_migrations.version` is the hard guarantee). The hash is a SHA-256 of the file's raw bytes, comments included, with no re-hash command; line endings are pinned to LF by `.gitattributes` so every checkout hashes the same bytes. A migration is frozen from its first application to the production database; until then it is reworked freely at the cost of a local reset. Because a frozen comment cannot follow the code, a migration comment states only the local _why_ of its change, as it stands: no planned evolution and no cross-cutting design, which this document owns and marks `(target)`. The `schema_migrations` table and the hash are the contract the Rust phase honors: the runner is reimplemented in Rust, not replaced by `sqlx-cli` `(target)`, and `database/src/migrate.test.ts` is the executable specification a reimplementation is checked against — each test creates a throwaway database on the local cluster and drops it, never sharing `ename_test` with the backend suite. A `no-transaction` migration (`CREATE INDEX CONCURRENTLY`) has neither the lock nor the rollback, and its pending re-check cannot close the window: it must be idempotent, and the runner is launched by a single job at a time.

**Tests.** `node:test`, run as integration tests against a real PostgreSQL — no DB mocks, no mocked services. A dedicated `ename_test` database is kept apart from `ename_dev` by the test environment file and by a guard in the test DB lifecycle helper that refuses to delete rows in any database whose name does not end in `_test`; the guard is the one that holds, since a `DATABASE_URL` exported in the shell outranks the file. Isolation is `TRUNCATE ... RESTART IDENTITY CASCADE` per test; `BEGIN`/`ROLLBACK` per test is excluded because it nests a SAVEPOINT under the code's own `withTransaction` and would hide real transactional behavior. Test files run sequentially (shared database) and close the pool after each file. Each test asserts only its layer's public surface. **API contract tests** drive the app via `app.fetch(request)` and observe only what an HTTP client sees. Nothing validates a response at runtime — the framework validates requests only — so a test that reads a body either compares it whole to a literal or reads it through the exported wire schema that declares it (`readJSON`, `readProblem`, in the API test helper), never through a hand-written type; the read fails when the body adds, omits or malforms a field, at any depth, though the schemas are not strict. **Service tests** come in three grains: each concept's **data-access primitives** are tested directly (insert-then-read round-trips), and a vocabulary declared in code — the event kind definitions, `SubjectKindSchema`, `KeyAlgorithmSchema` — is tested against the `CHECK` that enumerates it, in both directions, by reading the constraint from the catalog (`readCheckConstraintValues`, in the test DB lifecycle helper); the **write protocol** is tested at its own interface, with a real event kind (the `kind` CHECK admits no test kind), the real authentication of a platform or one the test controls, and a work the test controls, which makes every branch — a signer refused, replay, conflict, another signer's key, the race at the events insert, a domain error overlapping a winner — deterministic; a kind's `toOutcome` and `fromEvent` are pure rules, and their law is tested without a database on hand-built rows; and **use cases** are tested by running them and inspecting persisted state through the primitives (`findSubjects`, `findEnames`, `findEvents`), never raw `pool.query`. A kind's `rebuild` is tested beside its use case: the test runs the use case, empties the projections (`truncateProjections`, in the test DB lifecycle helper), rebuilds the log in `sequence` order and compares the rows read back with those the use case wrote; a homonym rebuilt with only the setup's events before it shows that the recorded `numberPart` is written, not allocated, which a full rebuild in log order would not. Each kind's tests also verify the signature of the events their use case stores, from the stored event alone (`isEventSignatureValid`). The walk over the whole log is tested beside it, in `application`, on use cases of every kind interleaved: the projections emptied and rebuilt at several batch sizes, each compared with the rows the use cases wrote. A use-case test does not re-test idempotency. Reading state back through the primitives is not circular: they carry their own round-trip tests. **Plumbing tests** cover `src/database/` at its own interface — the pool's handling of a lost idle connection, the transaction helper's nesting, the test-database guard — in raw SQL on an existing table, since no primitive is in reach below the Service layer. A log line a function emits through the logger it receives is part of its observable surface: a test captures it with a pino destination of its own — a logger built for the test, or a child of one swapped into the request once the middleware has bound it — and asserts on the lines it expects (the retry of a `number_part` collision, the error line behind an opaque 500), never by intercepting the root logger. A concurrency path is forced, not hoped for: the test holds a transaction open, starts the contender, waits until the catalog shows it blocked on the handover (`waitForLockedStatement`, in the test DB lifecycle helper), then commits. A burst whose outcome depends on scheduling states the values it rests on and what was measured; the test environment file sets the pool size it was measured at (`DATABASE_POOL_SIZE`). A test helper lives in the layer it serves — `src/database/testing.ts` for the database, `src/services/testing.ts` for the signers (the registry anchored, a platform accredited and a request signed through the real use cases, or, for the test of a primitive or an authentication, a platform or key row written directly), `src/api/testing.ts` for HTTP — and nowhere else; a test of a higher layer reaches a lower one's helper for its setup. An API test loads the app before any Service module: `@hono/zod-openapi` gives `.openapi()` only to the Zod schemas built after it loads, and the API wraps the Service's schemas.

## Infrastructure

**Hosting.** Scaleway, serverless: a Serverless Container for the backend (language-agnostic across Node and Rust) and Serverless SQL for the database. Node's cold start is higher than Rust's — plan a minimum instance count above zero once traffic is regular.

**Health probes.** `/health` is liveness: the process answers, nothing else is checked. It is the path of the Serverless Container's HTTP probe, which takes a failing instance out of rotation without restarting it `(target)`; a database outage then degrades the API (writes answer 503 Problem Details) instead of taking every instance out of rotation at once. `/health/deep` checks that the database answers a trivial query within a short bound; it serves monitoring, smoke tests and alerting, and is never wired to the orchestrator.

**Serverless SQL constraints.** Serverless SQL fronts each database with a PgBouncer in transaction mode and disables a set of PostgreSQL features. These are not reproducible on the local PostgreSQL, so the discipline is to avoid them by construction:

- Session state via `SET`/`RESET`/`DISCARD` is unreliable (connections are multiplexed between transactions) — set `statement_timeout` and the like through the driver's startup parameters, never a post-connection `SET`.
- `LISTEN`/`NOTIFY` has no delivery guarantee — excluded as a reliable mechanism; asynchronous messaging will go through a dedicated broker if the need arises.
- Session-level advisory locks have no guarantee (the lock stays on one server connection while the next statements run on others) — forbidden everywhere, the migration runner included. A transaction-level advisory lock (`pg_advisory_xact_lock`) lives and dies with its transaction and is usable; the application never coordinates through advisory locks (see Concurrency).
- No `PREPARE TRANSACTION`, session temporary tables, `REFRESH MATERIALIZED VIEW CONCURRENTLY` or security labels; DDL on roles and databases goes through the Scaleway API, not SQL.
- Queries are capped at 1 MB and transactions are expected to be short.
- About 40 extensions are supported — verify any dependency against the current list before committing to it.

This list ages with the product; reconfirm it periodically against the Scaleway documentation.

**Connection pool.** A single `pg.Pool` singleton in the Service layer. Its timeouts are hard-coded and identical in dev and prod: the 5 s `statement_timeout` is an implicit latency SLA that constrains index and query design — a query that exceeds it is a bug, or a legitimate batch that must opt out with a `SET LOCAL` in its own transaction. Its size comes from configuration (`DATABASE_POOL_SIZE`, low by default), because it follows the deployment, not the code. In production `(target)` it is set to the Serverless Container's concurrency per instance, so that no accepted request ever waits for a connection (a request holds at most one at a time), and the size times the maximum instance count stays under the Serverless SQL connection limit at the chosen allocation — a limit that scales with the allocation and is read from the console, not assumed. `application_name` is set so the service is findable in `pg_stat_activity` and Scaleway logs.

## Open questions

- **[Q-PORT-TRIGGER]** The explicit trigger for the Node → Rust port — calendar, event (second platform, security audit, traffic threshold), or first-of-both. Must be fixed and written down before the v1 release, or the port never self-triggers.
- **[Q-LOG-STRUCT]** The exact cryptographic structure of the public log (linear CT/Sigsum-style, sparse Merkle/CONIKS-style, or hybrid), the signed-tree-head scheme, publication frequency, bootstrap snapshots, and any external anchoring. To settle by prototyping during the Node phase; it conditions the log's public format and API surface.
- **[Q-CRYPTO-AGILITY]** The multi-century crypto-agility plan: SHA-256 and ECDSA P-256 will not last. The format must carry explicit suite versioning from v1 and a re-anchoring mechanism that preserves the commitment chain across a hash or signature change. Joint with [Q-LOG-STRUCT] and [Q-CRYPTO-IMPL].
- **[Q-REGKEY-MGMT]** Management of the registry key (HSM vs cloud KMS, possible k-of-n multi-signature, rotation, succession on loss or jurisdictional transfer). Near-irreversible once the first tree head is signed — settle before the v1 release.
- **[Q-REVOC-REASONS]** Whether revocations carry a codified reason (compromise, retirement, death) or stay opaque — it changes what a verifier can conclude about a signature made before the revocation. Tie with [Q-REVOC] in `ename-synthesis.md`.
- **[Q-RECOVERY-PROC]** The institutional framing of platform-mediated recovery as seen from the registry: effectiveness delays, re-verification requirements, contestation channel, audit. Distinct from the user-side [Q-KEYREC]; mostly regulation, with log-encoding implications.
- **[Q-OPERATION-KIND]** The relation between the operation a signer requests (`subject.register`) and the event kind the log records (`subject.registered`): each operation produces one kind, declared by the kind's definition and published in [Ename — Signature](./ename-signature.md), but the log stores only the kind, so a verifier maps it back. Whether the mapping is the right long-term form, or the log should record the operation itself, possibly renaming `kind` to `operation`, is open.
- **[Q-LEGAL-DEMANDS]** The registry's prepared stance on legal demands for erasure or rectification, given a public append-only log: some are structurally impossible to honor, others (a forced deactivation mark) remain possible. Prepare with legal counsel before the v1 release.
